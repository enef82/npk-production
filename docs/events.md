# Каталог доменных событий

Публичный контракт между модулями (см. `src/core/events/`, инварианты И1 и И4 в
`CLAUDE.md`). Меняется только с версионированием: правка существующей записи задним
числом запрещена — новое поле или новый смысл поля означает `version + 1` и новую запись
в этом каталоге, а не молчаливое изменение старой.

## Как публикуется событие

1. Прикладной модуль объявляет событие в своём `events.py` — dataclass, унаследованный
   от `src.core.events.base.DomainEvent`, с `event_type: ClassVar[str]` и, по умолчанию,
   `version: ClassVar[int] = 1`.
2. Сервис модуля вызывает `src.core.events.publisher.publish(event)` **внутри** уже
   открытой `transaction.atomic()`, в той же транзакции, где меняется состояние
   (инвариант И4). Вне транзакции `publish()` поднимает `PublishOutsideTransactionError`.
3. Другой модуль подписывается через декоратор `@subscribe("module.event_name")` из
   `src.core.events.registry` в своём `handlers.py`. Регистрация происходит сама при
   старте приложения (`EventsConfig.ready()` вызывает
   `autodiscover_modules("handlers")`) — `core.events` не импортирует ни один
   функциональный модуль напрямую.
4. Celery Beat каждые `EVENTS_DISPATCH_INTERVAL_SECONDS` секунд запускает
   `core_events.dispatch_pending_events` — диспетчер выбирает необработанные события
   пачкой и вызывает подписчиков. Ошибка одного обработчика не блокирует остальных и не
   теряет событие: счётчик попыток растёт, следующая попытка откладывается
   экспоненциально (`EVENTS_RETRY_BACKOFF_BASE_SECONDS` / `EVENTS_RETRY_BACKOFF_MAX_SECONDS`),
   а после `EVENTS_MAX_ATTEMPTS` попыток событие перестаёт выбираться автоматически и
   попадает в `python manage.py stuck_events` («требует внимания»).
   У задачи в `CELERY_BEAT_SCHEDULE` выставлен `expires = EVENTS_DISPATCH_INTERVAL_SECONDS`:
   если пачка обрабатывается дольше интервала, просроченные тики отбрасываются вместо
   накопления дублей в очереди — следующий тик всё равно подхватит те же необработанные
   события, потому что состояние живёт в БД, а не в самой задаче.
   «Уведомление» на этом шаге — только `logger.critical` и `stuck_events`, без внешнего
   канала (алерт/письмо/Slack) — решение и триггер пересмотра в
   `docs/adr/0007-opoveshchenie-o-zastryavshih-sobytiyah.md`.

## Формат имени события

`<модуль>.<сущность>_<действие_в_прошедшем_времени>`, например `contracts.contract_signed`.
Только строчные буквы, цифры и `_`. Тип события не меняется никогда — новая версия
схемы данных получает `version + 1`, а не новый `event_type`.

## Деньги в нагрузке — строкой

Денежная величина в `payload` передаётся **строкой** десятичного числа (`"1234567.89"`),
а не числом. JSON не знает типа `Decimal`, а `float` для денег запрещён инвариантом И6
(в том числе в промежуточных вычислениях). Публикующая сторона кладёт в событие
`Decimal`, база сериализует его в строку (`core.events.base._json_safe`); потребитель
разбирает строку обратно в `Decimal` — не в `float` и не через `float` по пути.


## Шаблон записи каталога

```text
### <event_type>

- **Версия:** 1
- **Публикует:** src.<модуль>
- **Когда:** <при каком переходе состояния публикуется>
- **aggregate_id:** <что это за идентификатор — id какой сущности>
- **payload:**
  - `поле` (тип) — описание
- **Подписчики:** <модуль> — <зачем>
```

## Реестр событий

### core_events.example.widget_touched — пример механизма, не бизнес-событие

- **Версия:** 1
- **Публикует:** `src.core.events.tests.support.WidgetTouched` — тестовый класс, живёт
  только в `tests/`, никогда не импортируется прикладным кодом.
- **Когда:** не публикуется в проде. Используется исключительно тестами
  `src/core/events/tests/` для проверки publish → outbox → dispatcher → подписчики,
  минуя прикладные модули (которых на момент реализации механизма ещё нет).
- **aggregate_id:** произвольный UUID, генерируется тестом.
- **payload:**
  - `note` (str) — свободный текст, для проверки сериализации payload.
- **Подписчики:** нет постоянных — тесты регистрируют и снимают свои через
  `registry.subscribe()` / `registry.clear()` (см. `tests/conftest.py`).

Реальные доменные события появятся здесь по мере реализации прикладных модулей —
каждое со своей записью по шаблону выше, в PR, который их вводит.

### identity.party_archived

- **Версия:** 1
- **Публикует:** `src.core.identity`
- **Когда:** при архивировании контрагента (`services.party.archive_party`) —
  `Party.status` переходит в `ARCHIVED`, в той же транзакции.
- **aggregate_id:** `Party.id`.
- **payload:** нет дополнительных полей — причина архивации остаётся в
  pghistory-контексте (`actor_context(actor_id, reason=reason)`), не дублируется здесь.
- **Подписчики:** нет постоянных.

### equipment.repair_closed

- **Версия:** 1
- **Публикует:** `src.equipment`
- **Когда:** при закрытии записи журнала аварий и ремонтов
  (`services.repair.close_repair`, в том числе «Провести ТО» —
  `services.repair.perform_maintenance`) — `Repair.status` переходит в `done`, в той же
  транзакции, что и простой в наработке суток и (для вида «ТО») запись
  `MaintenanceRecord`. Закрытая запись больше не правится, поэтому событие по одной
  записи публикуется ровно один раз.
- **aggregate_id:** `Repair.id`.
- **payload:**
  - `equipment_id` (UUID) — оборудование.
  - `date` (date, ISO) — дата ремонта: локальная дата начала простоя (`started_at`);
    на неё ложатся часы в табеле.
  - `number` (str) — номер записи (`АР-0001`), для аналитики `REP-…` и текста журнала.
  - `workers` (list) — исполнители: `[{employee_id (UUID), hours (str, Decimal)}]`,
    по убыванию часов; не пуст — без исполнителей запись не закрывается.
- **Подписчики:** `timesheet` — часы исполнителей в разноску `target=repair` на дату
  ремонта (`docs/spec/00-prilozhenie-proizvodstvo.md` §3.5); идемпотентность по
  `aggregate_id`.
