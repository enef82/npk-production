# 0009. Атомарная выдача номера: SELECT FOR UPDATE, а не последовательность PostgreSQL

## Контекст

`core.numbering` выдаёт номера документов (`Numerator`) по произвольному числу шаблонов,
создаваемых из админки в рантайме, с настраиваемой периодичностью сброса (пока: `NEVER`,
`YEARLY`). Задание прямо требует конкурентно-устойчивой атомарной выдачи и называет два
варианта на выбор: `SELECT FOR UPDATE` или последовательность PostgreSQL (`SEQUENCE`).

## Решение

`SELECT FOR UPDATE` над строкой `Numerator`, затем `get_or_create` + инкремент строки
`NumeratorCounter(numerator, period_key)`:

```python
with transaction.atomic():
    numerator = Numerator.objects.select_for_update().get(code=code, is_active=True)
    period_key = _period_key(numerator, when)
    counter, _ = NumeratorCounter.objects.select_for_update().get_or_create(
        numerator=numerator, period_key=period_key, defaults={"last_value": 0},
    )
    counter.last_value += 1
    counter.save(update_fields=["last_value", "updated_at"])
```

Блокировка строки `Numerator` первой сериализует **все** параллельные запросы по этому
`code` до коммита транзакции — поэтому последующий `get_or_create` на `NumeratorCounter`
безопасен даже ровно на границе периода: первый вызов в новом периоде создаёт строку
счётчика, уже не конкурируя ни с кем (проверено тестом на 50 параллельных потоках,
`src/core/numbering/tests/test_issue.py::test_конкурентная_выдача_номеров_не_даёт_дублей`,
с `@pytest.mark.django_db(transaction=True)`, чтобы блокировки реально состязались, а не
жили внутри одной обёрнутой в savepoint транзакции теста).

## Отвергнутая альтернатива: последовательность PostgreSQL (`CREATE SEQUENCE`)

- Нумераторы создаются динамически из админки в произвольном количестве, а
  последовательность — DDL-объект. Создавать `CREATE SEQUENCE` на каждую строку
  `Numerator` в рантайме — вне механизма миграций Django: неудобно бэкапить,
  интроспектировать через ORM, синхронизировать со схемой.
- Сброс по периоду для последовательности — это `ALTER SEQUENCE ... RESTART`, ещё один
  DDL-вызов, который пришлось бы дёргать по расписанию (Celery Beat на границе года).
  Риски: гонка ровно в момент сброса, если кто-то запрашивает номер в этот момент;
  сброс впустую, если в новом периоде номер так и не запросили (или, наоборот, попытка
  восстановить последовательность, которая ещё не создана, если год наступил, а первый
  документ выпущен позже). Строка `NumeratorCounter` для нового периода возникает лениво,
  ровно при первом реальном использовании — этого класса гонок и вырожденных случаев
  просто нет.
- Обычные Django-миграции управляют `Numerator` и `NumeratorCounter` единообразно, без
  ручного DDL и без специального кода синхронизации последовательности со строками.
- Цена подхода: `SELECT FOR UPDATE` сериализует выдачу номеров по одному нумератору —
  конкурентные запросы на один и тот же `code` ждут друг друга. Для внутренней ERP
  инженерной компании (номера договоров, заказов, актов) это не realистичная
  throughput-проблема: простота и корректность важнее для команды 1–2 разработчика.

**Версии проверены на PyPI на момент задачи:** зависимости-обёртки не требуются —
использованы штатные `django.db.transaction`/`select_for_update`, без новых пакетов.
