# 0029. Прод-контур: пять решений, которые иначе приняты были бы случайно

## Контекст

`docker-compose.yml` в корне — dev/CI-стек и сам себя объявляет непригодным для сети:
bind-mount кода вместо сборки, `runserver`, порты PostgreSQL/Redis/MinIO наружу,
Gotenberg без авторизации. Фронтенд в нём не участвует. Задание — задание ИС «прод-контур»,
спецификация машины — документ ИС «обкатка VDS»: офисный сервер `ubunty04` (`192.168.11.14`),
пятнадцать штатных пользователей, реальные заявки с первого дня — то есть на машине будут
оклады, себестоимость и наценки, восстановимые из ставок делением.

По §10 конституции документ идёт раньше кода. Пять вопросов ниже иначе решились бы
неявно, кодом первого черновика, а не осознанным выбором.

## 1. Файл из MinIO — отдаёт Django, не Caddy

Сейчас (`src/core/documents/selectors.py::get_download_url`, `src/core/documents/api/routers.py`,
эндпоинт `/{document_id}/link`) браузер получает **presigned S3-URL** и идёт за байтами
напрямую в MinIO, минуя Django. `AWS_S3_ENDPOINT_URL` (сейчас `http://minio:9000`,
docker-internal имя) буквально зашивается в подписанную ссылку как хост — если MinIO
не публикуется наружу, эта ссылка нерабочая по построению, не только в проде: это же
значение недостижимо и с телефона в офисной Wi-Fi-сети.

Более тонкая причина отказаться от presigned-URL даже при рабочем хосте:
`can_download` проверяется **один раз, в момент выдачи ссылки** (`routers.py`), а сама
ссылка остаётся действительной `DOCUMENTS_URL_TTL_SECONDS` (900 с) независимо от того,
что случится с правом доступа за это время — отозвали доступ, уволили сотрудника,
ссылку переслали. Для документов вроде КП с ценами и наценками это не гипотетический
риск, а ровно тот тип данных, ради которого во всём остальном документе настаивают
на HTTPS и разделении прав.

**Решение:** Django отдаёт файл сам, потоком, через `FileResponse` без чтения файла
целиком в память (`storage.open(document.file.name)` → `FileResponse(...)`), проверяя
право доступа **на каждый запрос байтов**, а не только на выдачу ссылки. `AWS_S3_ENDPOINT_URL`
в проде указывает на внутренний `http://minio:9000` и никогда не покидает docker-сеть —
Caddy о MinIO не знает вовсе. Это код часть C: заменить presigned-`url` в ответе `/link`
(или добавить рядом отдельный потоковый эндпоинт) на прямую отдачу содержимого.

**Честная цена:** воркеров у gunicorn четыре (докс. по памяти машины), и каждый
отдаваемый файл занимает воркер на всё время скачивания — не миллисекунды, как обычный
API-запрос, а секунды-десятки секунд на офисном канале. При 15 пользователях и файлах
до нескольких десятков мегабайт (см. `docs/adr/0022-...md`) это не узкое место сегодня,
но это осознанно принятая, а не незамеченная цена.

**Условие пересмотра** (конкретное, проверяемое): появление вложений размером
в сотни мегабайт (сейчас предел — 50 МБ, `INQUIRY_ATTACHMENT_MAX_SIZE_BYTES`), либо
первый зафиксированный случай, когда интерфейс не отвечает во время выгрузки/скачивания
из-за занятых воркеров. При срабатывании — переход на `forward_auth`, см. ниже.

**Отвергнуто:**

- Caddy проксирует отдельный путь (`/s3/*`) на MinIO, оставляя presigned-URL.
  Быстрее по нагрузке на Django-воркер, но: (а) требует зарезервировать сегмент пути
  в корневом неймспейсе домена навсегда, конфликтующий риск с Next.js/Django-роутами;
  (б) корректность SigV4-подписи через прокси (Host-заголовок, HTTPS-терминация на Caddy)
  нужно доказывать эмпирически на каждое изменение конфигурации — то самое место,
  где, по словам задания, «провалиться можно незаметно»; (в) не устраняет разрыв между
  моментом проверки права и моментом чтения байтов.
- `forward_auth` в Caddy — штатная директива: Caddy спрашивает у Django разрешение
  на конкретный объект (200/403), получив «да», сам проксирует байты из MinIO. Право
  проверяется на каждый запрос, **и** байты не идут через gunicorn — снимает именно
  тот минус выбранного варианта, что назван выше как честная цена. Не выбрано сейчас
  ровно потому, что цена пока не набралась: два движущихся места (Django для проверки
  права, Caddy+MinIO для байтов) вместо одного — лишняя сложность, пока её не
  окупает реальный трафик. Это и есть цель условия пересмотра выше — не отказ навсегда,
  а отказ пока.

### 1а. Реестр видимости сущностей — паттерн проекта, не частный случай (правка 18.09)

Первая версия решения 1 (часть C) проверяла право привязанного документа как
«пользователь аутентифицирован» — это не перенос старого поведения, а его дыра под
новым именем: presigned-URL раньше вообще не перепроверялся, и повторить это значит
объявить дыру закрытой, не закрыв её. Правка (часть E′) возвращает решение к
формулировке из п. 1 выше — «право проверяется на каждый запрос байтов» — буквально:
`can_download` (`src/core/documents/rules.py`) делегирует видимости сущности,
к которой привязан документ (заявка, расчёт), а не проверяет факт входа в систему.

`core.documents` не может импортировать `crm` (И1), поэтому не может напрямую
спросить «видит ли пользователь эту заявку». Решение — реестр чекеров
(`src/core/documents/registry.py`, экспортирован через `facade.py`):
вызывающий модуль регистрирует свою проверку видимости сам, в `AppConfig.ready()`
(`src/crm/apps.py` — `can_view_inquiry`/`can_view_quotation` для `crm.inquiry`/
`crm.quotation`). Документ, привязанный к типу сущности без зарегистрированного
чекера, остаётся закрытым (только загрузивший/администратор) — **не открытым**:
отсутствие регистрации — это отсутствие права, а не молчаливое разрешение.

Это не новый приём — `core.identity.registry` решает ту же задачу для профилей
`Party`/`Item` тем же способом (модуль ниже по слоям не может импортировать модуль
выше, вызывающий регистрирует себя сам при старте). Применённый второй раз, этот
приём стал **паттерном проекта**: следующему модулю, которому core.documents
понадобится для сущности со своим кругом видимости (не «любой аутентифицированный»),
пиши `register_entity_visibility_checker` в `ready()`, как это уже сделано для
`identity` и `documents` — не изобретай третий способ прокинуть проверку через
слои. В структуре модуля (CLAUDE.md §4) `registry.py` — часть публичной поверхности
наравне с `facade.py`: `facade.py` экспортирует то, что вызывающий модуль **читает**
у этого модуля, `registry.py` — то, что вызывающий модуль **отдаёт** этому модулю.

## 2. Тома PostgreSQL и MinIO — каталоги хоста, не именованные тома Docker

**Решение:** `/opt/npk-prod/data/postgres`, `/opt/npk-prod/data/minio` — bind-mount с хоста,
не `volumes:` секция. Причина не в бэкапе напрямую (ни `pg_dump`, ни `mc mirror` не читают
файлы тома — оба работают по протоколу сервиса, им всё равно, где физически лежат данные),
а в прозрачности для команды в 1-2 человека: `df -h`/`du -sh` показывают реальный размер
без `docker volume inspect`, каталог виден и копируется обычным `rsync`/`tar` как
дополнительная защита поверх логического бэкапа (пункт 5 части C), если логический
бэкап когда-нибудь придётся дополнить снимком файловой системы.

**Отвергнуто:** именованные тома Docker — «докер-идиоматично», но добавляет косвенность
без выгоды здесь: ни один процесс бэкапа не обращается к ним напрямую, а диагностика
(«сколько места занимает база») требует лишней команды вместо привычной.

## 3. Миграции — одноразовый сервис в compose, гонка исключена конструктивно

**Решение:** отдельный сервис `migrate` (`command: python manage.py migrate`,
`restart: "no"`), `web` объявляет `depends_on: migrate: condition: service_completed_successfully`.
Compose не запустит `web`, пока `migrate` не завершится с кодом 0 — гонка двух воркеров
на миграциях (задание прямо называет её «реальный способ получить половину применённой
схемы») исключена самим механизмом зависимости, а не соглашением между людьми.

**Отвергнуто:** миграция командой снаружи после `up -d`. Риск ровно тот, о котором
предупреждает задание: между `up -d` и ручным `make migrate` `web` уже поднят и может
начать обслуживать запросы против несмигрированной схемы. Черновик документ ИС «обкатка VDS»
(«Обновления») изначально предлагал именно эту последовательность; заказчик поправил
раздел сам после того, как это было названо в согласовании ADR — сейчас там уже нет
отдельной команды `migrate`, только `build`/`up -d`, с объяснением, что миграцию берёт
на себя одноразовый сервис композа.

## 4. Порядок старта и healthcheck'и — тот же паттерн, что в dev-compose, продолженный на новые сервисы

Дев-стек уже держит цепочку `depends_on: condition: service_healthy` (постгрес/редис/
minio-init/gotenberg → web/worker/beat). Прод-контур продолжает тот же приём, а не
изобретает новый:

- `migrate` → `depends_on: postgres: service_healthy`;
- `web` → `depends_on: migrate: service_completed_successfully`, `redis/minio/gotenberg: service_healthy`;
- `worker`, `beat` → `depends_on: postgres, redis: service_healthy` (как сейчас);
- `frontend` → без внешних зависимостей на старте (Next.js standalone не обращается
  к БД напрямую), healthcheck — `GET /` на самом контейнере;
- `caddy` → `depends_on: web, frontend: service_healthy`.

Для `web` healthcheck — отдельный `/healthz`, не `/api/docs`. Изначальный выбор
(переиспользовать существующий эндпоинт) был неверным: `/api/docs` — страница
документации API, а не индикатор здоровья процесса, и её рано или поздно закроют
под аутентификацию (это уже прямая обязанность после решения о полной публикации
системы, ADR 0030) — тогда healthcheck начнёт падать по причине, не имеющей отношения
к здоровью приложения, просто потому что два разных смысла делили один URL.
`/healthz` — пять строк кода (`django.http.HttpResponse` с `200`, без обращения к БД:
он проверяет, что процесс жив, а не что вся система работает — готовность PostgreSQL
уже проверяется его собственным healthcheck'ом, дублировать её здесь незачем),
без `auth`, вне `/api/*`, чтобы публикация/защита API не могла случайно задеть его.

## 5. Сертификат — HTTP-01 по умолчанию, `tls internal` для локальной проверки, DNS-01 только описан

Caddy получает сертификат сам (встроенный ACME-клиент), настройка по умолчанию — HTTP-01:
работает на штатном образе `caddy`, ничего собирать не нужно. Для локальной проверки
контура (часть D, без реального DNS) — `tls internal`, включаемый переменной окружения
(`CADDY_TLS_MODE=internal|http01` или аналогично), чтобы не обращаться к боевому
Let's Encrypt ни разу в рамках этого задания — лимиты выдачи не то, чем стоит рисковать
до того, как имя действительно приведено к машине.

**Подтверждено 17.09, после первой редакции этого решения:** заказчик проверил маршрут
маркером, поднятым прямо на `192.168.11.14` — `ee3.kt96.ru:80/443` и `85.12.241.104:80/443`
доходят до машины. Проброс существует, сценарий A (система публикуется в интернет)
подтверждён, не предположение. HTTP-01 — не запасной вариант на случай сценария A,
а единственный нужный: провайдер DNS `kt96.ru` вопрос снят полностью, `xcaddy` не нужен.

DNS-01 всё равно **описывается, не реализуется** — он не нужен при подтверждённом
сценарии A, но остаётся в документе на случай, если проброс когда-нибудь снимут
(имя останется только для офиса). Тогда потребуется сборка Caddy с плагином конкретного
DNS-провайдера через `xcaddy` — штатный образ провайдеров не содержит; провайдер
пока не назван, это отдельная будущая правка.

**Важное следствие подтверждённого проброса, не связанное напрямую с сертификатом:**
на маршрутизаторе нет hairpin NAT — с самой `192.168.11.14` обращение к её же внешнему
адресу даёт `Connection refused`. Всё, что работает изнутри контура (healthcheck'и,
Gotenberg, любой код, строящий и сам же дёргающий абсолютный URL), обязано использовать
внутренние имена сервисов Docker, а не `ee3.kt96.ru` — иначе такой код будет работать
с рабочего места и ломаться на самом сервере, и разница проявится не на старте, а через
неделю. Это ограничение уже отражено в решениях 1 и 4 выше (внутренний `AWS_S3_ENDPOINT_URL`,
`GOTENBERG_URL` на docker-имя, healthcheck на `localhost` внутри контейнера).

### 5а. HTTP-01 зафиксирован явно, tls-alpn-01 отключён (правка 18.09 — реальная выкатка)

При первом реальном запуске на `192.168.11.14` (часть F задания) боевой сертификат не
выпускался: каждая попытка виснет по таймауту (`http2: timeout awaiting response headers`)
на шаге challenge, ни разу не доходя до `finalize` или скачивания цепочки. Staging-сертификат
(рехёрсл, п. 4 задания) при этом выпустился успешно с той же сети — то есть порт 80, DNS
и конфигурация в порядке, дело не в них.

Три факта сложились в механизм. Caddy обращается к ACME по HTTP/2 — все шаги одной сессии
(`newAccount`, `newOrder`, challenge, `finalize`) идут по одному TCP-соединению, которое
Caddy держит между шагами; при этом единичные проверочные запросы (`curl`, `wget`) всегда
открывают новое соединение и потому всегда проходили — расхождение вводило в заблуждение,
пока проверка не различала эти два случая. Тип challenge переключился после первой удачной
попытки с `http-01` на `tls-alpn-01`: для `http-01` шаг между `newOrder` и уведомлением
«готов» — мгновенная запись токена, для `tls-alpn-01` — генерация валидационного сертификата
и поднятие обработчика на 443, заметная пауза. Рабочая гипотеза: этой паузы достаточно, чтобы
NAT-шлюз офисной сети сбросил простаивающий поток без RST — клиент пишет в мёртвое соединение
и виснет в ожидании заголовков до таймаута. Проверяемое следствие — на `http-01` (короткая
пауза) выпуск проходит, что и наблюдалось на staging, — совпало.

**Первый шаг (применён 18.09):** `tls { issuer acme { email …; disable_tlsalpn_challenge } }`
в `Caddyfile` — фиксирует единственную схему, которая когда-либо срабатывала, вместо того
чтобы полагаться на автовыбор Caddy между типами challenge. Явный `issuer acme` не наследует
глобальный `email` — продублирован внутри блока, иначе адрес в ACME-аккаунте потерялся бы
молча и уведомления об истечении сертификата остались бы ненастроенными без единого сигнала
об этом. Побочный эффект: явный `issuer` заменяет список issuer'ов целиком, а не дополняет
его — ZeroSSL как запасной вариант (Caddy пробовал его по умолчанию третьим шагом, тоже
безуспешно, с отдельной непрояснённой ошибкой) из конфигурации ушёл вместе с этим.

**Второй шаг (планируется отдельно, только если первый подтверждён работающим на реальном
продлении, не только на первичной выдаче):** `GODEBUG=http2client=0` в окружении контейнера
`caddy` — переводит Go-клиент ACME на HTTP/1.1, который переоткрывает соединение на каждый
шаг сессии. Это снимает причину (переиспользуемое долгоживущее соединение), а не обходит
её удачным совпадением таймингов у `http-01` — полагаться только на «пауза у http-01
достаточно короткая» нельзя, это перестанет быть верным при любой правке настроек шлюза
офисной сети, а определить причину придётся заново, уже без контекста этой сессии.

Оба шага применяются и проверяются по одному, не одновременно — иначе при успехе неизвестно,
какой из них сработал, а один из двух остаётся в проекте навсегда.

Локальная проверка (часть D, `tls internal` через `tls-local.d/`) с явным `issuer acme`
одновременно не используется — для локального прогона `tls`-блок в `Caddyfile` временно
закомментировать.

## Отвергнутые альтернативы (сводно)

- Presigned-URL через Caddy-прокси на MinIO — п. 1.
- `forward_auth` в Caddy — п. 1, отложено до условия пересмотра, не отказ навсегда.
- Именованные тома Docker — п. 2.
- Ручной `make migrate` после `up -d` — п. 3.
- Healthcheck `web` на `/api/docs` вместо отдельного `/healthz` — п. 4, первоначальный
  выбор пересмотрен: `/api/docs` не индикатор здоровья и рискует уйти под аутентификацию.
- DNS-01 сейчас — п. 5, не нужен при подтверждённом сценарии A, остаётся описанием
  на случай будущего пересмотра проброса.
