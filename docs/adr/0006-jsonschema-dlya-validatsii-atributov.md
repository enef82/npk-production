# ADR 0006. Валидация JSONB-атрибутов профилей через библиотеку `jsonschema`

**Статус:** принято
**Дата:** 2026-08-19
**Связано:** `docs/spec/02-yadro-identichnosti.md` §3.5, §4

---

## Контекст

Профили модулей (`PartyProfile`/`ItemProfile`) хранят модульные атрибуты в JSONB-поле
`attributes`. Чтобы это поле не превратилось в бесконтрольную свалку, значения в нём
валидируются по JSON Schema, которую модуль регистрирует под парой `(app_label,
category)` в `AttributeSchema`. Схемы редактируются администратором данных через
Django Admin как обычный JSON-документ — нет статической, известной заранее формы.

## Решение

Добавлена зависимость `jsonschema==4.26.0` (актуальная версия на PyPI на момент
задачи; `requires-python >=3.10`, совместима с проектным пином `3.13`). Транзитивно
тянет `attrs==26.1.0`, `jsonschema-specifications==2025.9.1`, `referencing==0.37.0`,
`rpds-py==2026.6.3` (версии зафиксированы `uv.lock`, отдельно в `pyproject.toml`
не пинуются — как и остальные транзитивные зависимости в проекте). Каждая из
четырёх проверена по GitHub Advisory Database отдельно, не только `jsonschema`
целиком: security-advisory нет ни у одной. `requires-python` у всех четырёх
совместим с проектным `3.13` (`attrs >=3.8`, `jsonschema-specifications >=3.9`,
`referencing >=3.10`, `rpds-py >=3.11`) — уже подтверждено и практически: `uv sync`
разрешил и установил всё под интерпретатор 3.13.15 без конфликтов.
`rpds-py` — расширение на Rust, но публикует готовые wheels под linux (manylinux),
Windows и macOS; сборочный тулчейн на CI и в контейнере не нужен. Для `mypy --strict`
добавлен `types-jsonschema==4.26.0.20260518` в dev-зависимости.

Меры, обязательные из-за того, что схемы приходят от пользователя через админку,
а не зашиты статически в коде:

- **диалект зафиксирован явно** — `Draft202012Validator`, без автоопределения по
  ключу `$schema` внутри пользовательской схемы;
- **сетевое разрешение `$ref` запрещено** — валидатору передаётся явный
  `referencing.Registry()` без `retrieve`-коллбэка. Без этого `$ref` на произвольный
  URL внутри схемы, сохранённой через админку, превращался бы в SSRF: сервер сходил
  бы туда, куда скажет автор схемы;
- **сама схема валидируется при сохранении** — `AttributeSchema.clean()` вызывает
  `Draft202012Validator.check_schema()`. Без этого синтаксически некорректная схема,
  сохранённая через админку, либо ронял(а) бы валидацию атрибутов в рантайме на
  каждой попытке сохранить профиль, либо — что хуже — молча пропускала бы всё подряд.

## Отвергнутая альтернатива

**Ручная реализация подмножества JSON Schema** (`type`, `required`, `enum`,
`minimum`/`maximum`, `pattern` — без `$ref`, `anyOf`, `additionalProperties` и
прочего). Отвергнуто: частичная реализация стандарта опасна тем, что молча
пропускает данные с незнакомыми ей ключевыми словами — автор схемы напишет
`additionalProperties: false` или `anyOf`, валидатор не узнает эти ключи и не
станет по ним проверять, а невалидные данные пройдут. Валидация, которая думает,
что работает, хуже её отсутствия: без валидации известно, что данные не проверены,
с сломанной — нет. Подмножество и не осталось бы минимальным: первой понадобится
`anyOf`, затем вложенные объекты, затем `format` — каждое расширение добавляет
собственный код со своими багами, что противоречит требованию проекта к скучному,
предсказуемому коду (раздел 1 CLAUDE.md).

## Следствия

**Положительные.** Валидация соответствует спецификации JSON Schema Draft
2020-12 целиком, а не тому подмножеству, которое успели реализовать. Ошибки
пользователю формулируются на русском для частых случаев (`required`, `type`,
`enum`, `minimum`, `maximum`, `pattern`) через словарь-переводчик в
`core/identity/services/attributes.py`; для остальных ключевых слов используется
исходное сообщение `jsonschema`.

**Отрицательные.** Новая зависимость с транзитивным Rust-расширением
(`rpds-py`) — увеличивает поверхность `pip audit`/security-мониторинга и время
сборки образа при отсутствии кеша wheels для целевой платформы (на практике не
проявилось: manylinux/win_amd64 wheels для `rpds-py` есть).

Проверка security-advisory при добавлении зависимости — снимок на момент задачи,
не постоянная защита: уязвимость в `attrs` или `rpds-py` полгода спустя никто
не заметит без повторной проверки. Поэтому в `.github/dependabot.yml` включён
еженедельный мониторинг `uv`-зависимостей (и ежемесячный — GitHub Actions) —
разовая проверка на этом ADR превращена в постоянную, а не осталась только
записью в истории задачи.

## Триггер пересмотра

Пересмотреть, если `jsonschema` перестанет поддерживаться или в проекте
понадобится валидация без сторонних зависимостей вообще (например, при переносе
в окружение без доступа к PyPI на этапе сборки).
