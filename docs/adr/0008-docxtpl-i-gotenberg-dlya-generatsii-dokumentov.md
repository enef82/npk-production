# 0008. Генерация документов: DOCX-шаблоны (docxtpl) + Gotenberg, а не HTML-шаблоны (WeasyPrint)

## Контекст

`core.documents` должен уметь рендерить документ из шаблона с подстановкой контекста и
отдавать его как PDF (`docs/spec/03-platforma.md` §2.4). В задании на выбор были названы
`docxtpl` и «WeasyPrint или headless LibreOffice». Технически это не три равноценных
варианта одного слоя: `docxtpl` рендерит `.docx`, а WeasyPrint — рендерер HTML/CSS→PDF,
который `.docx` вообще не читает. Значит развилка не «чем конвертировать DOCX в PDF», а
на уровень выше — «в каком формате хранятся шаблоны и кто их правит»:

- **DOCX-шаблоны + docxtpl** — шаблон это обычный `.docx` с `{{ переменными }}` внутри
  текста, правит юрист или бухгалтер прямо в Word.
- **HTML-шаблоны + WeasyPrint** — шаблон это HTML/CSS, правит разработчик, конвертация
  прямая (WeasyPrint сам растеризует HTML в PDF, второй сервис не нужен).

## Решение

DOCX-шаблоны через `docxtpl`. Документы этого проекта — договоры, счета, УПД — по смыслу
задачи (`CLAUDE.md` §1) остаются в зоне ответственности юриста/бухгалтера, а не
разработчика: они должны иметь возможность поправить формулировку в Word без правки кода
и деплоя, а согласованный с контрагентом договор часто нужно отдать именно как
редактируемый `.docx`, а не только как PDF. HTML-шаблоны на это не годятся в принципе.

Конвертация `.docx → PDF` — через **Gotenberg** (модуль LibreOffice внутри Gotenberg,
эндпоинт `/forms/libreoffice/convert`), отдельным контейнером в `docker-compose.yml`,
а не headless LibreOffice, запускаемый `subprocess`-ом внутри образов `web`/`worker`:

- образы `web`/`worker` не разбухают на ~1 ГБ и не тянут LibreOffice в каждую сборку CI;
- вызов — обычный HTTP-запрос (`httpx`), а не управление подпроцессом с таймаутами,
  зомби-процессами и временными файлами;
- headless LibreOffice плохо переносит параллельные конвертации в одном процессе —
  у Gotenberg это уже решено;
- обновляется независимо от приложения (`gotenberg/gotenberg:8.36.0`).

Цена — ещё один сервис в `docker-compose.yml`. Для команды 1–2 человека это дешевле,
чем сопровождение подпроцессов в двух образах.

Движок конвертации изолирован за одной функцией — `core.documents.services.generation.
render_to_pdf(docx_bytes) -> bytes` — это единственное место, которое знает о Gotenberg.

**Важно по безопасности:** Gotenberg не имеет аутентификации по умолчанию. В проде порт
наружу не публикуется — сервис виден только `web`/`worker` по имени на внутренней сети. Порт
`3000` в `docker-compose.yml` — это только локальная разработка и CI (тот же файл к проду
отношения не имеет: там MinIO вместо Yandex Object Storage, тот же принцип и для Gotenberg);
он нужен, потому что `pytest` (`uv run`, на хосте) обращается к Gotenberg напрямую в
интеграционном тесте (`@pytest.mark.integration`, `test_generation.py`).

## Отвергнутые альтернативы

- **WeasyPrint + HTML-шаблоны** — отклонено: не подходит по формату шаблонов (см. выше),
  а не по качеству рендеринга. Уместно для документов, которые органически HTML (веб-отчёт
  без потребности в правке в Word) — такого требования в задании нет.
- **Headless LibreOffice через `subprocess` в образах `web`/`worker`** — отклонено:
  раздувает образы, требует ручного управления процессом и временными файлами, хуже
  масштабируется на параллельные конвертации. См. обоснование Gotenberg выше.

**Версии проверены на PyPI/Docker Hub на момент задачи (не по памяти):**
`docxtpl==0.20.2`, `httpx==0.28.1` (клиент для вызова Gotenberg — до этой задачи в проекте
не было HTTP-клиента), `gotenberg/gotenberg:8.36.0`.
