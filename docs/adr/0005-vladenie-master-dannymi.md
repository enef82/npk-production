# ADR 0005. Владение мастер-данными и направление синхронизации с 1С

**Статус:** принято
**Дата:** 2026-08-19
**Связано:** ADR 0002 (обмен с 1С), `docs/spec/02-yadro-identichnosti.md` §3.9–3.10

---

## Контекст

Приложение работает в облаке, 1С расположена on-premise за VPN-туннелем. Часть
справочных данных ведётся и будет продолжать вестись в 1С силами бухгалтерии
и кадровой службы независимо от того, что мы построим.

Нужно решить для каждого класса данных: где находится источник правды и в какую
сторону течёт синхронизация. Решение принимается один раз и определяет устройство
интеграции на всё время жизни системы.

### Фактический ландшафт 1С (август 2026)

| База | Роль | В контуре интеграции |
|---|---|---|
| **1С:Бухгалтерия 8.3**, конфигурация доработана — дописаны блоки производства и закупок | основной источник: контрагенты, номенклатура, деньги, банк, закупки, производство | да, `system = "bp"` |
| **1С:ЗУП**, отдельная база | штатное расписание, кадровые события, отсутствия, начисления | да, `system = "zup"` |
| **1С:УНФ 3.0.13** | используется мало | нет — вне контура до отдельного решения |

**Принцип опоры на типовые объекты.** Конфигурация Бухгалтерии доработана, поэтому
обновления, которых при регламентированном учёте много, будут конфликтовать с
доработками. Интеграция строится на типовых объектах (`Справочник.Контрагенты`,
`Справочник.Номенклатура`, банковские документы). Дописанные объекты используются
только там, где без них не обойтись, и каждый такой случай фиксируется отдельно
с указанием риска поломки при обновлении. Доработки поддерживаются, OData по ним
включается по мере надобности.

### Целевое состояние

Принято стратегическое решение: **оперативный контур выводится из Бухгалтерии**,
чтобы анализ операционной деятельности вёлся в одной системе.

| Система | Целевая роль |
|---|---|
| ERP (наша) | весь оперативный контур: CRM, договоры, закупки, склад, производство, проекты, труд, управленческие финансы |
| 1С:Бухгалтерия | только регламентированный учёт: проводки, налоги, отчётность. Первичку получает из ERP |
| 1С:ЗУП | расчёт зарплаты. Табель получает из ERP, кадры отдаёт в ERP |
| 1С:УНФ | выводится из эксплуатации |

**Владение мигрирует по фазам.** До запуска модуля источником остаётся дописанный
блок Бухгалтерии, после — наша система. Направление обмена по этому блоку
разворачивается на противоположное.

| Блок | До фазы | После фазы |
|---|---|---|
| Закупки | БП → ERP (чтение истории) | ERP → БП (первичка для учёта), Ф3 |
| Производство | БП → ERP | ERP → БП, Ф8 |
| Продажи, счета | БП → ERP | ERP → БП, Ф2 |
| Реквизиты, адреса | БП → ERP | без изменений, БП остаётся владельцем |
| Кадры, штатка | ЗУП → ERP | без изменений |
| Табель | — | ERP → ЗУП, Ф4 |

### Правило переключения

**Переключается точка ввода, а не место хранения.** В момент запуска модуля ввод
данных переходит в ERP полностью и одномоментно; Бухгалтерия продолжает получать
всё необходимое для учёта, но из ERP, а не руками.

Параллельный ручной ввод в обе системы не допускается ни на один день — это самый
частый способ провалить внедрение и получить два расходящихся набора данных.
Откат при неудаче — возврат ввода в БП, а не одновременная работа.

Каждая фаза, замещающая дописанный блок, содержит явный шаг вывода этого блока
из эксплуатации: отключение ввода, перенос истории, проверка полноты.

## Решение

**Односторонне из 1С. ERP хранит реплику только для чтения и не пишет туда никогда:**

- банковские реквизиты контрагентов;
- адреса контрагентов;
- штатное расписание, должности, кадровые события, утверждённые отсутствия;
- банковские выписки.

**Владеет ERP, в 1С не выгружается:**

- профили модулей (закупочный, коммерческий, финансовый, технологический);
- вся транзакционная работа: лиды, сделки, КП, договоры, заявки, заказы поставщикам,
  проекты, производственные заказы;
- разноска труда по объектам затрат.

**Владение совместное:**

- идентичность контрагентов и номенклатуры. Первичная загрузка — из 1С. Контрагент,
  заведённый менеджером в CRM, живёт только в ERP до момента, когда понадобится
  в учёте, и выгружается в 1С при первом счёте. Реализуется в Фазе 2.

  Права на запись у служебной учётной записи подтверждены (август 2026), то есть
  выгрузка осуществима. **Наличие прав не меняет момент выгрузки.** Отложенная
  выгрузка выбрана не из-за ограничений доступа, а по существу: квалифицированный
  лид может никогда не стать заказчиком, и справочник контрагентов в 1С — учётный
  документ, в котором не должно быть записей без единого документа. Ранняя выгрузка
  засоряла бы его и порождала дубликаты именно там, где мы от них уходим.

### Требования безопасности при записи в 1С

Право записи меняет радиус поражения при ошибке: дефект в коде синхронизации
или неудачный сгенерированный скрипт способны повредить учётную базу.

- **Две служебные учётные записи, а не одна.** Чтение — регулярное и массовое,
  запись — редкая и точечная. Разные учётные записи ограничивают ущерб от ошибки
  в читающем коде, который выполняется на порядки чаще.
- **Права на запись выданы точечно** — только на объекты, куда действительно
  выгружаем, а не полным доступом к конфигурации.
- **Запись только через явный сервис с идемпотентностью** по `ExternalRef`.
  Массовых операций записи не существует; каждый объект выгружается отдельно
  и результат фиксируется.
- **Режим `dry-run` обязателен** — прогон, показывающий, что было бы записано,
  без фактической записи. Первый реальный обмен выполняется только после него.
- **Разработка и тестирование — на копии базы 1С, не на рабочей.** Это относится
  и к отладке, и к прогону тестов интеграции.

**Из ERP в 1С:**

- табель по видам рабочего времени и база распределения затрат — Фаза 4.
  Передаются часы и доли, не рубли (см. спецификацию кадров).

### Реализация

Три уровня хранения для всего, что реплицируется:

```
1С (владелец) → реплика в ERP (read-only) → снимок внутри документа
```

Соответствие идентификаторов — таблица `core_integrations.ExternalRef`,
не поле в `Party`.

Поля-реплики недоступны для редактирования ни через API, ни через админку;
в интерфейсе показываются неактивными с пометкой «из 1С» и кнопкой «обновить».

## Отвергнутые альтернативы

**Не хранить реквизиты локально, тянуть из 1С по OData на лету.**
Отвергнуто по четырём причинам. Облачный контур получил бы жёсткую рантайм-зависимость
от on-premise: обрыв туннеля или регламентные работы в 1С означали бы невозможность
напечатать договор или выставить счёт. Список из пятидесяти договоров превратился бы
в пятьдесят обращений через туннель. JOIN с чужой системой невозможен, поэтому любая
аналитика в разрезе реквизитов или регионов отпадает. Каждый сеанс OData занимает
клиентскую лицензию 1С.

Решающий довод — историчность. Договор, подписанный год назад, содержал действовавшие
тогда реквизиты. При обращении по ссылке повторная печать показала бы текущие, то есть
юридически значимый документ менялся бы задним числом.

**Двусторонняя синхронизация всех справочников.**
Отвергнуто: требует разрешения конфликтов при одновременной правке в двух системах.
Для команды из одного-двух разработчиков это неподъёмная по сложности и по объёму
тестирования задача, а выигрыш умозрительный.

**Ведение реквизитов в ERP с выгрузкой в 1С.**
Отвергнуто: бухгалтерия продолжит работать в 1С независимо от наших намерений,
и реквизиты всё равно будут править там. Попытка сделать ERP владельцем привела бы
к тому, что реальные изменения проходили бы мимо системы.

## Следствия

**Положительные.** Недоступность 1С не блокирует работу — все нужные данные локальные.
Самый тяжёлый класс интеграционных конфликтов не возникает вовсе, потому что двух
пишущих сторон нет. Документы воспроизводимы: снимок реквизитов не меняется.

**Отрицательные.** Данные в ERP отстают от 1С на интервал синхронизации, и пользователи
будут это замечать. Нужен экран расхождений — что изменилось в 1С с момента последней
синхронизации, — иначе устаревшая реплика обнаружится только по факту неверного платежа.
Правка реквизитов требует переключения в 1С, что для пользователя выглядит неудобством
и потребует объяснения при обучении.

**Требуется реализовать помимо самой синхронизации:** кнопку принудительного обновления
записи, журнал синхронизаций с диагностикой, экран расхождений, блокировку записи
на уровне сервисов, а не только интерфейса.

## Триггер пересмотра

Решение пересматривается целиком, если появится требование вести реквизиты
в ERP — например, при отказе от 1С или переносе кадрового учёта в нашу систему.
До тех пор одностороннее направление не обсуждается в частном порядке
для отдельных полей.
