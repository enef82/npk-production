# 0016. Вложения заявки: без справочника типов и без антивирусной проверки

## Контекст

Шаг 10а Фазы 1а: исходные данные заявки (ТЗ, ПД, спецификации, опросные листы,
требования к подрядчику, архивы, письмо заказчика) кладутся в систему, а не остаются
в почте. Механику даёт `core.documents` — `Document` + `DocumentLink` с
`entity_type = "crm.inquiry"`. Два решения по объёму требовали фиксации, потому что оба
раза очевидным выглядел более «полный» вариант.

**Классифицировать ли вложения.** Напрашивался справочник `DocumentType` со значениями
«ТЗ», «ПД», «спецификация», «опросный лист», «архив», «требования», «прочее» — и поле
выбора в форме загрузки.

**Проверять ли файлы антивирусом.** Напрашивалась проверка загружаемого файла перед
записью в бакет — ClamAV или внешний сервис.

## Решение

**Справочника типов вложений нет.** Заводится один тип `crm_inquiry_attachment`
(«Вложение к заявке»), пользователь его не выбирает и не видит — его проставляет сервис.
`DocumentType` здесь не классификатор, а носитель ограничений: лимит размера (50 МБ) и
список допустимых MIME (пустой — «любой, кроме исполняемых»). Вместо классификации —
свободное `Document.description` («ТЗ ред. 2», «архив ПД»), поиск по подстроке.

Справочник заводится тогда и только тогда, когда по его значению что-то происходит:
своё согласование, свой срок хранения, своя проверка, свой отчёт. У типов вложений
заявки ничего этого нет — в отличие от `LossReason`, где по значению считается отчёт
«почему проигрываем». Справочник без такого потребителя даёт только выпадающий список,
в котором семь раз из десяти выберут «прочее», а форму — длиннее. Список вложений
принципиально не формализуем: договор, произвольное письмо, архив, требования к
подрядчику. Если через год выяснится, что ТЗ надо отличать от прочего (например, чтобы
отвечать «по какой редакции считали»), для этого есть `DocumentLink.role`, сейчас
пустой — заполнять его «на будущее» запрещает §6 CLAUDE.md.

**Антивирусной проверки нет.** Файлы приходят снаружи, лежат в приватном бакете,
отдаются только по временной подписанной ссылке; сервер их не исполняет и не
распаковывает. Риск — на машине того, кто скачал файл, тот же, что при получении его
почтой сегодня. Единственная проверка на приёме — запрещающий список исполняемых
расширений и MIME (не разрешающий: перечислить `dwg`, `rar`, `7z`, `p7s` и всё
остальное, что пришлют с комплектом, заранее нельзя, а пустой разрешающий список молча
роняет загрузку на всём).

## Условия пересмотра

- **Справочник типов** — когда у типа вложения появится собственное поведение:
  отдельный маршрут согласования, срок хранения, отчёт в разрезе типа. Тогда значение
  переезжает в `DocumentLink.role`, а не в новую модель.
- **Антивирус** — когда вложения начнут открываться или распаковываться на стороне
  сервера (предпросмотр, авторазбор спецификаций), либо появится требование ИБ.
  Место для проверки — сервис загрузки в `core.documents`
  (`store_upload`/`validate_against_doc_type`), одна точка на все модули; это отдельная
  задача, заранее ничего закладывать не нужно.

## Отвергнутые альтернативы

- **Справочник типов с полем выбора в форме** — отклонено: нет потребителя значения,
  форма длиннее, «прочее» доминирует; роль в `DocumentLink` покрывает будущую нужду.
- **Автоопределение «новой редакции» по совпадению `description`** — отклонено:
  описание свободное и написано для людей, опечатка молча породила бы вторую линию
  версий. Новая редакция — отдельное действие `add_inquiry_document_version`.
- **Антивирус на приёме сразу** — отклонено: проверка постфактум на неисполняемый в
  системе файл — работа без сегодняшнего потребителя; при появлении нужды делается в
  `core.documents`, а не в `crm`.

**Новых зависимостей нет.** Всё делает уже подключённый `core.documents`
(`django-storages`, ADR 0008/0015).
