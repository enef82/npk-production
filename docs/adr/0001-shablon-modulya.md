# 0001. Эталонный модуль и шаблон тиражирования для восьми оставшихся

## Контекст

Фаза 0 заканчивается модулем-образцом: `procurement`, срез «Поставщики»
(спецификация закупок ИС (IS_ERP, 30-procurement)). Задача шага 11 — не просто собрать этот один модуль, а
зафиксировать *шаблон*, по которому дальше будут собираться `crm`, `contracts`, `hr`,
`finance`, `projects`, `production`, `intelligence` (и полная спецификация закупок
в Фазе 3). Команда — 1–2 разработчика: без явного, проверяемого шаблона каждый новый
модуль заново изобретает форму сервиса, форму admin, форму events.py — и со временем
модули расходятся по мелочам, которые ничего не решают, кроме как отнимают время на
чтение чужого кода.

Срез «Поставщики» выбран для образца намеренно широко: он трогает все восемь частей
раздела 4 CLAUDE.md разом — профиль поверх ядра идентичности, собственный справочник со
своим деревом, конечный автомат статусов, права, публикацию события и подписку на чужое,
admin с сервис-роутингом, API с курсорной пагинацией, два экрана на типовых
фронтенд-компонентах.

## Решение

### Что копируется дословно (структура, не смысл)

| Приём | Где смотреть в `procurement` | Откуда взят паттерн |
|---|---|---|
| Структура каталогов модуля | `src/procurement/` целиком | раздел 4 CLAUDE.md |
| Регистрация профиля через `AppConfig.ready()` | `apps.py` | было с шага 4 |
| `facade.py` — только то, что реально нужно другим модулям, докстринг объясняет кто первый потребитель | `facade.py` | `core.identity.facade`, `core.accounts.facade` |
| Голый `@transition` в модели, вся логика в `services/` | `models/vendor_profile.py` (FSM) | `core.approvals.models.request.ApprovalRequest` |
| `services/` — функции с `actor_id: UUID`, `transaction.atomic()` + `actor_context()`, права проверяются вызывающей стороной (роутером/admin), не сервисом | `services/vendor_profile.py`, `services/category.py`, `services/candidate.py` | `core.identity.services.party` |
| `events.py` — frozen dataclass `DomainEvent`, `event_type` по формату `<модуль>.<сущность>_<действие>` | `events.py` | `core.approvals.events`, `docs/events.md` |
| `handlers.py` — `@subscribe("...")`, обработчик идемпотентен и не публикует событий сам | `handlers.py` | `docs/events.md`, `core.events.registry` |
| `rules.py` — предикаты через `core.accounts.facade` для ролей, локальные предикаты для прав, специфичных модулю | `rules.py` | `core.accounts.rules`, `core.identity.rules` |
| `admin/` — `save_model` роутит в сервис, `readonly_fields` на поля, которыми владеет сервис, custom-поле формы вместо `Meta.fields` там, где `ModelForm.save_m2m()` обошёл бы сервис | `admin/__init__.py` (`VendorProfileAdminForm`) | `core.identity.admin.PartyAdminForm` |
| `api/routers.py` — курсорная пагинация через `core.common.pagination`, не `@paginate`; права — `if not predicate(request.auth): raise PermissionDenied` перед вызовом сервиса | `api/routers.py` | `core.identity.api.routers` |
| Фронтенд — список и карточка целиком на `DataTable`/`EntityCard`/`EntityForm` без правок компонентов | `frontend/app/(protected)/vendors/` | `frontend/app/(protected)/parties/` |
| Тесты — по разделу 8 CLAUDE.md, `assertNumQueries` на списки, `IntegrityError`/`ProtectedError`/`TransitionNotAllowed` на инварианты, `Client` вместо мока на admin/API | `src/procurement/tests/` | `core.identity.tests`, `core.approvals.tests` |

### Что специфично для закупок (не копировать смысл, только форму)

- Сами модели: `VendorProfile` (расширение профиля с шага 4), `PurchaseCategory`
  (дерево), `VendorCandidate` (живёт только в модуле, без дедупликации).
- Набор FSM-переходов и его источники/цели (`DRAFT → ON_REVIEW → APPROVED ⇄ SUSPENDED`,
  `BLOCKED` только через повторную проверку) — у каждого модуля свой процесс.
- Роли `снабженец`/`руководитель снабжения` (`core.accounts.groups.PROCUREMENT_OFFICER`/
  `PROCUREMENT_HEAD`) и то, что `force`-промоушен переиспользует право
  `core_identity.force_create_party`, а не заводит отдельную роль «администратор
  данных» — конкретное решение для конкретной операции, не общий приём.
  дублировать в другой модуль эту связку бессмысленно; для другого модуля будут
  другие роли и, возможно, другое переиспользуемое право.
- Продвижение кандидата — только Django Admin, без API (спецификация закупок ИС (IS_ERP, 30-procurement) §7).
  Это решение о конкретном экране, не о шаблоне API вообще.

### Расширения ядра, потребовавшиеся по ходу (не специфичны закупкам, но и не часть шаблона —
### разовые дополнения `core`, на которые будущие модули могут опираться)

- `identity.party_archived` — `core.identity` не публиковал это событие до шага 11;
  `archive_party()` теперь публикует его в той же транзакции. Любой будущий модуль,
  которому нужно реагировать на архивацию контрагента, подписывается на готовое
  событие, а не изобретает его заново.
- `core.accounts.groups.PROCUREMENT_HEAD` и предикаты `is_procurement_officer`/
  `is_procurement_head` в `core.accounts.rules`, экспортированные через
  `core.accounts.facade` — второй потребитель facade после `core.documents.rules`,
  подтверждает, что паттерн «роль → предикат → facade» воспроизводим. Оба
  предиката, как и `is_administrator`, пропускают суперпользователя вне
  зависимости от роли (`user.is_superuser or ...`) — без этого обнаружилось при
  проверке в браузере: сидовый суперпользователь `make seed` не состоит ни в одной
  группе, и без байпаса не смог бы пройти ни один из статусных переходов
  поставщика — ни через API, ни через admin.
- `src/core/events/tests/conftest.py`: автоиспользуемая фикстура `_clean_registry`
  раньше просто вызывала `registry.clear()` до и после каждого теста — это стирало
  не только тестовые подписки, но и обработчики, зарегистрированные один раз при
  старте приложения (`autodiscover_modules("handlers")`). До шага 11 в системе не
  было ни одного настоящего постоянного обработчика (`docs/events.md` прямо
  фиксировал: «реальные события появятся по мере реализации прикладных модулей»),
  поэтому дефект был скрыт. `procurement.handlers.block_vendor_on_party_archived` —
  первый; фикстура теперь снимает снимок реестра перед `clear()` и восстанавливает
  его после, не трогая поведение тестов `core.events`. Без этого исправления любой
  тест из `core.events.tests`, случайно выполнившийся раньше теста с реальным
  обработчиком в одной сессии `pytest`, «отключал» этот обработчик до конца сессии.

## Отвергнутая альтернатива: генератор — Django management-команда в `core.common`

Задание и первоначальный план называли путь `src/core/common/management/commands/
new_module.py`. По факту `core.common` не зарегистрирован в `INSTALLED_APPS` (в нём
нет `apps.py` — это обычный пакет с общими утилитами, а не Django-приложение), и
Django management-команды обнаруживаются только внутри установленных приложений.
Заводить `core.common` как полноценное приложение ради одной команды, которая не
трогает ORM, — лишняя сущность. Генератор — `scripts/new_module.py`,
обычный Python-скрипт (`uv run python scripts/new_module.py <name> "<verbose_name>"`),
без зависимости от Django-раннера. Функционально ничего не меняется: тот же
результат, тот же интерфейс запуска что и раньше по сложности.

## Замер времени

Оценка по этой сессии — единственный агент, без параллельной работы человека,
хронология по естественным границам между частями задачи (не поминутный таймер).
Годится как ориентир порядка величины для планирования Фазы 1, не как точная метрика.

| Часть | Что входило | Относительная доля |
|---|---|---|
| Ресёрч и согласование архитектуры | Изучение существующих модулей-образцов (identity, approvals, accounts, events), несколько раундов уточнений с постановщиком по расхождениям спеки/задания/факта (событие `identity.party_archived`, `core-independence`, `core-layers`, отсутствие `CustomerProfile`, статус `LegalEntity`) | ~30% |
| Модели + миграция | `VendorProfile` (FSM), `PurchaseCategory`, `VendorCandidate`, `models/choices.py`, одна миграция | ~7% |
| Сервисы + роли/права | `services/vendor_profile.py`, `category.py`, `candidate.py`, `rules.py`, расширение `core.accounts` | ~12% |
| Selectors/facade/events/handlers | Плюс расширение `core.identity` (событие архивации) и фикс `core.events.tests.conftest` | ~8% |
| Admin | Формы, custom-view продвижения кандидата, права | ~10% |
| API | `routers.py`/`schemas.py`/`filters.py` | ~6% |
| Тесты | 26 тестов `procurement` + переезд/переписывание тестов механизма профилей в `tests/` (корневой) | ~15% |
| Фронтенд | Список + карточка на типовых компонентах, e2e-спека | ~6% |
| Проверка в браузере + фикс | Реальный запуск стека в Docker, ручной прогон экрана — нашёл дефект инвалидации кеша React Query, не видимый ни `tsc`, ни `eslint`, ни pytest (см. `docs/checklist-novyy-modul.md` §8.7) | ~4% |
| Документация + генератор | Этот ADR, чек-лист, `scripts/new_module.py`, каталог событий, roadmap | ~5% |

Самая дорогая часть — не код, а согласование архитектурных решений с постановщиком до
того, как код написан (30%). Для Фазы 1, где шаблон уже зафиксирован и большинство
таких вопросов закрыто этим ADR, ожидаемое соотношение должно сместиться в сторону
кода: см. `docs/checklist-novyy-modul.md`. Проверка в браузере — маленькая доля
времени (4%), но единственный шаг, поймавший реальный, наблюдаемый пользователем
дефект; остальные проверки (`tsc`, `eslint`, pytest, mypy, `lint-imports`) были
зелёными при этом дефекте всё время — пропускать её не стоит ради экономии этих 4%.

**Версии проверены на PyPI на момент задачи:** новых зависимостей не введено — весь
модуль собран на уже зафиксированных в `pyproject.toml` пакетах (`django-fsm-2==4.2.4`,
`django-pghistory==3.9.2`, `rules==3.5`, `django-ninja==1.6.3`).
