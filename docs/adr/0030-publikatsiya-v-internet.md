# 0030. Система публикуется в интернет полностью, без ограничения админки по адресам

## Контекст

Проверка 17.09 (документ ИС «обкатка VDS») подтвердила: проброс `80/443` с `ee3.kt96.ru`
на `192.168.11.14` существует, сценарий A. Django Admin и `/api/docs` становятся
доступны из интернета наравне с самим приложением, если их не ограничить отдельно.

**Рекомендация:** оставить `/admin` и `/api/docs` доступными только с адресов офисной
сети (например, `@office { remote_ip 192.168.11.0/24 }` в Caddyfile, снаружи — 404).
Довод: админка — самая ценная мишень на всей системе (полный доступ к данным без
объектных прав `rules`), цена ограничения нулевая для штатной работы — обоим ресурсам
не нужен доступ из командировки, туда ходит администратор из офиса. `/api/docs` та же
логика: раскрывает всю схему API анонимно.

## Решение

Рекомендация **отклонена заказчиком 17.09**: публиковать систему полностью, без
ограничения по адресам. Обе точки — `/admin` и `/api/docs` — доступны из интернета
на равных с остальным приложением.

Раз дешёвая мера не принята, компенсирующие меры становятся частью этого решения,
а не отдельным пожеланием на потом:

1. **Ограничение частоты попыток входа — `django-axes==8.3.1`**, разрешение на
   зависимость дано заказчиком 18.09. Блокировка по связке «учётная запись + адрес»
   (`AXES_LOCKOUT_PARAMETERS = [["username", "ip_address"]]` — вложенный список,
   не плоский: один IP, перебирающий разные логины, не блокирует их друг через
   друга). Порог и окно — в настройках (`AXES_FAILURE_LIMIT`, `AXES_COOLOFF_TIME_HOURS`),
   не в коде, по умолчанию 5 попыток/1 час — не решение заказчика, разумный старт.
   Действует и в dev-окружении: перебор пароля стоит проверять тестами, не только
   на бою.
2. **Пароли пятнадцати учётных записей — генерируются командой бутстрапа**, не
   принимаются аргументом и не выбираются человеком («Иванов2026» не проходит).
3. **Настройки Django для публичного контура** — `DEBUG=False`, `ALLOWED_HOSTS`,
   `CSRF_TRUSTED_ORIGINS`, `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE`,
   `SECURE_CONTENT_TYPE_NOSNIFF`, `X_FRAME_OPTIONS`, HSTS начиная с часа (не года,
   без `preload`, без `includeSubDomains` — домен `kt96.ru` не наш целиком).
4. **`unattended-upgrades`** на сервере — только security-репозиторий, без
   автоматической перезагрузки.
5. **Неудачные входы пишутся в журнал приложения** — адрес и время, сигнал
   `user_login_failed` (техническая задача, не бизнес-логика — запрет §5 на сигналы
   сюда не относится). Без этого условие пересмотра ниже невыполнимо: нельзя заметить
   серию попыток, которую никто не записывает.
6. **Бэкап обязателен с первого дня** (уже часть ADR 0029, п. 2) — публичная машина
   рискует не только утечкой, но и шифровальщиком.

**Условие пересмотра** (конкретное, проверяемое, не «когда-нибудь»): первая
зафиксированная в журнале (мера 5) серия неудачных попыток входа с внешнего
(не `192.168.11.0/24`) адреса. При срабатывании — вернуться к рекомендации выше
(ограничение `/admin`/`/api/docs` по адресам) как к немедленной мере, независимо
от того, готов ли к этому моменту `django-axes`.

## Отвергнутые альтернативы

- **Ограничение `/admin`/`/api/docs` по IP офисной сети** — это и есть отклонённая
  рекомендация, см. выше; отклонена заказчиком, не мной.
- **`fail2ban` на уровне SSH/сети вместо ограничения на уровне приложения** — не
  решает задачу: атака идёт на веб-вход, не на SSH (он уже закрыт публикации,
  ADR 0029 закрыл прямые порты БД/Redis/MinIO), а `fail2ban` по логам Caddy —
  более грубый инструмент, чем `django-axes` на уровне учётной записи, и это отдельная
  зависимость уровня ОС, не проекта. Не отвергнуто навсегда — если `django-axes`
  разрешение не получит, это следующий кандидат.
