# 0010. Объектные права в админке откладываются, переносится только модельный уровень

## Контекст

Задание шага 9 предполагало, что админка уже использует
`rules.contrib.admin.ObjectPermissionsModelAdmin` для объектных прав, и требовало
аккуратно развести MRO при объединении с `unfold.admin.ModelAdmin`, чтобы перенос
не сломал молча уже работающую проверку прав на объект.

Проверка кодовой базы на момент шага 9 показала, что предпосылка неверна: все
`ModelAdmin` во всех модулях ядра до этого шага наследовались от плоского
`django.contrib.admin.ModelAdmin`. `django-rules` подключён как backend
(`AUTHENTICATION_BACKENDS = ["rules.permissions.ObjectPermissionBackend", ...]`,
шаг 6) и предикаты (`@rules.predicate`) написаны в нескольких модулях
(`documents.can_download`, `approvals.can_act_on_step`, `accounts.is_administrator`
и другие), но ни один предикат ни разу не зарегистрирован как именованное право
через `rules.add_perm(...)`, и `user.has_perm(...)` не вызывается нигде в проекте —
ни в API, ни в админке. Переносить в админке было нечего.

## Решение

Объектные права в админке в шаге 9 не подключаются. Перенос на `unfold.admin.ModelAdmin`
делается для всех админок механически, без объединения с `ObjectPermissionsModelAdmin`.
Вместо этого шаг 9 покрывает регрессионным тестом то, что реально уже работает и что
unfold мог сломать молча при подмене базового класса, — **модельные** права
(`has_view_permission`/`has_change_permission`/`has_delete_permission`, стандартный
механизм `django.contrib.auth.models.Permission`): пользователь без права `view`/`change`
получает 403 на список и на форму изменения, пользователь с правом — 200, проверено на
нескольких админках (не одной).

**Почему не подключить объектные права заодно, раз всё равно переносим базовый класс:**
для большинства моделей ядра фактическое правило доступа — «только администраторам»,
а это ровно то, что уже даёт модельный уровень прав, объектный уровень здесь ничего не
добавляет. Единственный кандидат с реальной идеей объектного правила —
`core.documents.can_download` («доступ у загрузившего или у администратора») — сам
заглушка: целевая модель («права на документ выводятся из прав на привязанную сущность»,
`docs/spec/03-platforma.md` §2.6) сознательно не реализована, пока нет ни одного
подключённого функционального модуля-потребителя. Подключать объектные права в админке
поверх этой заглушки означало бы зацементировать временное правило вместо целевого.

## Триггер пересмотра

Первый экран админки, где разным пользователям должны быть видны разные строки одной
модели (не просто «есть доступ / нет доступа» на уровне модели). Реалистично — Фаза 1
(справочники в разрезе подразделений) либо момент, когда `core.documents.can_download`
заменяется на вывод прав из привязанной сущности (`docs/spec/03-platforma.md` §2.6,
первый реальный потребитель `core.documents` из функциональных модулей). В этот момент
и делается разбор MRO `unfold.admin.ModelAdmin` + `rules.contrib.admin.ObjectPermissionsModelAdmin`
вместе с тестом на 403/200 по конкретному объекту — по обычной дисциплине, а не заранее.

## Обновление: наступило (шаг 3 Фазы 1а, `crm.CalculationRequest`)

спецификация CRM ИС (IS_ERP, 10-crm) §3.3/§6 потребовал первые в проекте объектные предикаты — не один,
а два: `is_request_assignee` (специалист правит своё задание и не правит чужое) и
`is_inquiry_project_manager` (любое действие внутри заявки — выдача задания, приёмка,
возврат — принадлежит руководителю проекта именно **этой** заявки, а не любому
руководителю проекта в системе: иначе назначение ответственного перестаёт что-либо
решать). Разбор MRO, которого ждал этот ADR, не понадобился — по причине, которую
стоит зафиксировать явно, а не молчаливо обойти.

**`is_inquiry_project_manager` — конъюнкция, не замена роли.** Сигнатура —
`(user, inquiry: Inquiry | None)`, не `CalculationRequest`: предикат в первую очередь
о владении заявкой, и годится сразу для всех действий внутри неё, а не только для
`CalculationRequest`. Проверяет membership в группе `PROJECT_MANAGER` **и**
`employee.id == inquiry.project_manager_id` — назначение `Inquiry.project_manager` без
роли в группе не подменяет её. Замещение — только через
`crm.services.inquiry.assign_project_manager` (право `is_technical_director`,
разрешено до `CALCULATING` включительно), не размытием права на действие.

**Почему `ObjectPermissionsModelAdmin` не подключён и сейчас.** Кейс `crm` — не тот
триггер, который описан выше. Здесь не нужна фильтрация списка («разным пользователям
видны разные строки») — чтение задания открыто любому аутентифицированному
(спецификация CRM ИС (IS_ERP, 10-crm) §6), значит `get_queryset` не сужается. Нужна только проверка на
запись по конкретному объекту при отдельных действиях (`issue_calculation_request`,
`start_calculation`, `submit_calculation`, `accept_calculation`, `return_calculation`).
А это Django даёт из коробки: `ModelAdmin.has_change_permission(request, obj=None)`
уже получает `obj`, когда он известен, — второй параметр появился в Django задолго до
этого шага и не имеет отношения к `django-rules`. Кейс, ради которого заводился
`rules.contrib.admin.ObjectPermissionsModelAdmin` (согласование `has_perm(obj)` через
бэкенд `rules.permissions.ObjectPermissionBackend` со списочной фильтрацией), здесь не
возникает — MRO решать было нечего.

**Что реализовано.** `crm.rules.is_request_assignee`/`is_inquiry_project_manager` —
обычные `@rules.predicate`, как и весь остальной вокабуляр модуля (`is_sales_manager`
и т.д.); они **не** зарегистрированы через `rules.add_perm(...)`, и `user.has_perm(...)`
по-прежнему нигде не вызывается — тот факт из первой версии ADR не изменился.
Предикаты вызываются напрямую, кодом приложения, в двух местах с одинаковым
результатом для каждого действия:

- `crm.admin.CalculationRequestAdmin` — `save_model` (выдача) и `accept_view`/
  `return_view` проверяют `is_inquiry_project_manager(request.user, obj.inquiry)`,
  `start_view`/`submit_view` проверяют `is_request_assignee(request.user, obj)`; любой
  отказ поднимает `django.core.exceptions.PermissionDenied` (→ 403) до вызова сервиса.
  `has_change_permission` проверяет оба предиката через `or` — либо назначенный
  специалист, либо руководитель проекта заявки видит форму. `crm.admin.InquiryAdmin`
  проверяет `is_technical_director` для правки `project_manager` тем же приёмом, что
  и для `scope`;
- `crm.api.routers` — `issue`/`accept`/`return_request` вызывают
  `is_inquiry_project_manager(request.auth, inquiry)`, `start`/`submit` вызывают
  `is_request_assignee(request.auth, obj)`, тот же `PermissionDenied`, тот же HTTP 403.

Два предиката, по два места вызова на каждое действие, идентичное поведение —
«предикат обязан работать одинаково в API и в админке» (спецификация CRM ИС (IS_ERP, 10-crm) §6) выполнено
без единой строки `django-rules`-специфичного кода в админке.

**Пересмотр этого решения (не первой версии ADR) наступит**, когда у какой-то модели
понадобится собственно списочная фильтрация по объектному праву — тогда и потребуется
`get_queryset` вместе с `has_perm(obj)`/`ObjectPermissionsModelAdmin`, а не раньше.
