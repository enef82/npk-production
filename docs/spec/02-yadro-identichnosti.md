# Спецификация: ядро идентичности

**Приложения:** `core.identity` (метка `core_identity`)
**Реализуется:** шаги 3 и 4 Фазы 0
**Термины:** `docs/spec/glossary.md`, раздел 2

---

## 1. Назначение и границы

Ядро идентичности отвечает на один вопрос: **является ли это тем же самым объектом**.
Больше ни на какой.

Классический единый справочник ERP неповоротлив потому, что смешивает идентичность
(меняется раз в жизни) и обогащение (меняется у каждого отдела по-своему и постоянно).
Здесь они разведены: общий не справочник, а **идентификатор**.

### Не делает

- Не хранит коммерческие, закупочные, производственные и учётные атрибуты — они в профилях.
- Не хранит историю цен, поставок, сделок — это транзакционные данные модулей.
- Не хранит банковские реквизиты, лимиты, отсрочки, категории, ставки НДС.
- Не знает ни об одном функциональном модуле (инвариант И1).
- Не обогащает данные из внешних источников — это делает `core.integrations`,
  результат передаёт сервису создания.

### Правило расширения

**`Party` — семь полей, `Item` — шесть.** Желание добавить восьмое означает, что нужен
профиль. Тест `test_ядро_party_имеет_ровно_семь_полей` защищает это механически.

## 3. Объекты

### 3.1 `Party` — контрагент

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7, PK | `uuid.uuid7()` из stdlib |
| `inn` | CharField(12), blank | 10 знаков для ЮЛ, 12 для ИП и ФЛ, пусто для нерезидента; контрольная сумма проверяется |
| `kpp` | CharField(9), blank | только у ЮЛ; у ИП, ФЛ и нерезидентов пусто |
| `legal_name` | CharField(512) | полное юридическое наименование |
| `short_name` | CharField(255) | рабочее имя, по нему ищут |
| `party_type` | `PartyType` | |
| `status` | `PartyStatus` | |

Плюс `created_at` / `updated_at` из `TimeStampedModel` — служебные, в счёт семи не идут.

```python
class PartyType(models.TextChoices):
    LEGAL     = "legal",     "Юридическое лицо"
    ENTREPRE  = "entrepre",  "Индивидуальный предприниматель"
    PERSON    = "person",    "Физическое лицо"
    FOREIGN   = "foreign",   "Нерезидент"

class PartyStatus(models.TextChoices):
    DRAFT    = "draft",    "Черновик"
    ACTIVE   = "active",   "Активен"
    BLOCKED  = "blocked",  "Заблокирован"
    ARCHIVED = "archived", "Архив"
```

**Ограничения БД:**

```python
constraints = [
    UniqueConstraint(
        fields=["inn", "kpp"],
        condition=~Q(status="archived") & ~Q(inn=""),
        name="core_identity_party_uniq_active_inn_kpp",
    ),
    CheckConstraint(   # КПП только у юрлиц
        condition=Q(party_type="legal") | Q(kpp=""),
        name="core_identity_party_kpp_only_for_legal",
    ),
]
indexes = [
    GinIndex(fields=["short_name"], opclasses=["gin_trgm_ops"],
             name="core_identity_party_name_trgm"),
]
```

Условная уникальность решает три задачи сразу: архивные записи не блокируют
пересоздание, нерезиденты без ИНН не конфликтуют друг с другом, а активные
дубликаты по ИНН физически невозможны.

Нерезиденты остаются вне защиты уникальности — для них работает только нечёткий
поиск и дисциплина. Это принято сознательно.

### 3.2 `Item` — номенклатура

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7, PK | |
| `code` | CharField(64) | уникален глобально |
| `name` | CharField(512) | |
| `item_type` | `ItemType` | изделие / материал / услуга |
| `base_uom` | FK → `UnitOfMeasure` | PROTECT |
| `status` | `ItemStatus` | draft / active / archived |

GIN-индекс с `gin_trgm_ops` на `name`.

### 3.3 `UnitOfMeasure`

`code`, `name`, `okei_code` (код ОКЕИ для обмена с 1С), `is_active`.
Наполняется сидом: шт, компл, кг, т, м, м², м³, л, ч, усл.ед.

### 3.4 `Contact` — контактное лицо

`party` (FK, CASCADE), `full_name`, `position_title`, `phone`, `email`,
`is_primary`, `is_active`. Строковые поля — `blank=True`, не `null`.

### 3.5 `AttributeSchema`

| Поле | Назначение |
|---|---|
| `app_label` | какому модулю принадлежит схема |
| `category` | к какой категории сущностей применяется |
| `schema` | JSONField — валидная JSON Schema |
| `is_active` | |

Уникальность по `(app_label, category)`.

### 3.6 `Address` — адреса контрагента

Связь «один ко многим»: у контрагента одновременно есть юридический, фактический,
почтовый адреса, адреса складов и точек доставки.

`party` (FK, CASCADE), `address_kind` (`AddressKind`: legal / actual / postal /
delivery / warehouse), `full_address`, `fias_id` (blank), `is_primary`, `is_active`,
`valid_from`, `valid_to`.

Юридический адрес приходит из ЕГРЮЛ при обогащении и не редактируется вручную.
Живёт в ядре, потому что нужен договорам, финансам и логистике одинаково.

### 3.7 `BankAccount` — банковские реквизиты

Тоже «один ко многим»: расчётный, транзитный, закрытые, счета в разных банках.

`party` (FK, PROTECT), `account_number`, `bic`, `bank_name`, `corr_account`,
`currency`, `is_primary`, `is_active`, `valid_from`, `valid_to`.

В ядре, потому что реквизиты нужны договорам (печать), финансам (платежи)
и закупкам (расчёты с поставщиками), и ни один модуль не может иметь своё мнение
о номере счёта. Модульные атрибуты — «проверен службой безопасности», «заблокирован
для платежей», лимиты — идут в профиль соответствующего модуля, не сюда.

> **`Address` и `BankAccount` — реплики только для чтения.** Владелец данных — 1С,
> синхронизация односторонняя. В ERP эти записи не создаются и не редактируются
> ни через API, ни через админку: поля показываются неактивными с пометкой «из 1С»
> и кнопкой «обновить». Правки вносятся в 1С. Подробности — ADR 0005.

### 3.8 Куда кладётся то, чего нет в ядре

**Критерий попадания в `Party` или `Item`.** Все четыре условия сразу:

1. нужно, чтобы установить тождество двух записей;
2. используется каждым модулем хотя бы для отображения;
3. имеет ровно одно значение;
4. модули не могут расходиться в том, каким оно должно быть.

Не прошло хотя бы одно — поле идёт в профиль или в связанную таблицу.

| Данные | Куда | Почему не в ядро |
|---|---|---|
| Описание, комментарии | профиль модуля | каждый отдел пишет своё (условие 4) |
| Банковские счета | `core_identity.BankAccount` | много значений (условие 3) |
| Адреса | `core_identity.Address` | много значений (условие 3) |
| Контактные лица | `core_identity.Contact` | много значений |
| Отсрочка, инкотермс, рейтинг | `procurement.VendorProfile` | нужно одному модулю (условие 2) |
| Сегмент, отрасль, менеджер | `crm.CustomerProfile` | то же |
| Кредитный лимит, налоговый режим | `finance.CounterpartyProfile` | то же |
| ОКПД2, ставка НДС, статья затрат | `finance.AccountingItemProfile` | то же |
| Маршрут, нормы, допуски | `production.TechItem` | то же |
| История цен, поставок, сделок | таблицы модуля | транзакционные данные, не справочные |

**Ограничение на семь и шесть полей касается колонок `Party` и `Item`, а не числа
таблиц в `core.identity`.** Добавить связанную таблицу в ядро — нормально, если она
проходит условия 1, 2 и 4. Добавить колонку — только через ADR с обоснованием
по критерию и обновлением эталонного списка в тесте.

### 3.8.1 Одно лицо в нескольких ролях

Контрагент часто является одновременно заказчиком и поставщиком. Это не коллизия,
а штатный случай: один `Party` с одним ИНН, несколько профилей — `crm.CustomerProfile`,
`procurement.VendorProfile`, `finance.CounterpartyProfile`. Реквизиты, адреса
и контактные лица общие, потому что живут в ядре.

**Разделение статусов.** У ядра свой статус, у каждого профиля свой, и смешивать
их нельзя:

| | Отвечает на вопрос | Примеры |
|---|---|---|
| `Party.status` | можно ли вообще иметь дело с этим лицом | ликвидация, мошенничество, блокировка службой безопасности |
| Статус профиля | можно ли работать с ним **в этой роли** | срывает сроки → блок как поставщика; не платит → стоп-отгрузка как заказчику |

Связь односторонняя: **архивирование или блокировка в ядре делает контрагента
непригодным во всех ролях**, а блокировка профиля о состоянии ядра не говорит ничего.

Механика: профили, у которых есть собственное состояние, переводятся в заблокированное
подпиской на `identity.party.archived`. Профили без состояния не делают ничего —
их непригодность следует из состояния ядра, потому что обращаться к профилю
архивированного контрагента бессмысленно по определению.

**Собственный статус заводится в профиле только там, где модулю есть что им выражать.**
У поставщика он нужен: на проверке, приостановлен, заблокирован службой безопасности.
У признака «это наше юрлицо» выражать нечего. Асимметрия здесь — замысел, а не пробел;
добавлять статус ради единообразия не следует.

Практическое следствие, которое легко упустить: блокировка службой безопасности —
это статус **ядра**. Если провести её через закупочный профиль, отдел продаж
об этом не узнает и продолжит отгружать.

**Роль определяется документом, а не контрагентом.** Договор знает свою сторону
(с покупателем или с поставщиком), один и тот же `Party` фигурирует в обоих видах.
Признака «это поставщик» на самом `Party` нет и быть не должно.

**Взаимозачёт не выполняется автоматически.** Дебиторская и кредиторская
задолженность по одному контрагенту — разные счета бухучёта, сворачиваются только
актом взаимозачёта. Финансовый модуль показывает их раздельно; свёрнутое сальдо —
справочной строкой, не заменяющей ни одну из сумм в реестре на оплату.

### 3.9 Соответствие с внешними системами

У 1С собственный идентификатор объекта — `Ref_Key` (GUID) в OData. Хранить его полем
в `Party` нельзя по двум причинам: это восьмая колонка, и ядро начало бы знать
о конкретной внешней системе. Соответствие живёт снаружи, в `core.integrations`:

```python
class ExternalRef(models.Model):
    system       = models.CharField("Система", max_length=16)    # onec, dadata, edo
    entity_type  = models.CharField("Тип сущности", max_length=32)  # party, item
    local_id     = models.UUIDField("Наш идентификатор", db_index=True)
    external_key = models.CharField("Ключ во внешней системе", max_length=64)
    synced_at    = models.DateTimeField("Синхронизировано", null=True, blank=True)

    class Meta:
        constraints = [
            UniqueConstraint(fields=["system", "entity_type", "external_key"],
                             name="core_integrations_externalref_uniq_external"),
            UniqueConstraint(fields=["system", "entity_type", "local_id"],
                             name="core_integrations_externalref_uniq_local"),
        ]
```

Одна таблица обслуживает 1С, ДаData, ЭДО и всё, что появится позже.
С появлением этой модели `core.integrations` перестаёт быть простым пакетом
и становится Django-приложением с меткой `core_integrations`.

### 3.10 Владение данными и направление синхронизации

Полное обоснование — ADR 0005. Кратко:

| Данные | Владелец | Направление |
|---|---|---|
| Банковские реквизиты, адреса | 1С | 1С → ERP, односторонне |
| Штатное расписание, кадровые события, отсутствия | 1С | 1С → ERP, односторонне |
| Банковские выписки | 1С | 1С → ERP, односторонне |
| Идентичность контрагента и номенклатуры | совместно | первичная загрузка из 1С; новые из ERP выгружаются в 1С при первом счёте (Фаза 2) |
| Профили модулей | ERP | не выгружаются |
| Сделки, договоры, закупки, проекты | ERP | не выгружаются |
| Табель и база распределения затрат | ERP | ERP → 1С (Фаза 4) |

**Три уровня хранения реквизитов:**

```
1С — владелец
 │  синхронизация по расписанию и по требованию
 ▼
ERP — локальная реплика, read-only
 │  копирование значений в момент выпуска документа
 ▼
Договор, счёт, акт — снимок реквизитов внутри документа
```

Снимок обязателен: договор, подписанный в прошлом году, должен при повторной печати
показывать реквизиты, действовавшие на дату подписания, а не текущие. Ссылка вместо
копии означала бы, что юридически значимый документ меняется задним числом.

## 4. Профили

### 4.1 Абстрактные базы

```python
class PartyProfile(models.Model):
    party      = models.OneToOneField(
        "core_identity.Party", on_delete=models.PROTECT,
        related_name="%(app_label)s_profile", verbose_name="Контрагент",
    )
    attributes = models.JSONField("Атрибуты", default=dict, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        abstract = True

    def clean(self) -> None:
        validate_against_schema(self.attributes, self.app_label, self.category)
```

`ItemProfile` — аналогично, с `item` вместо `party`.

### 4.2 Реестр профилей

Ядро не имеет права импортировать модули (инвариант И1), поэтому профили
регистрируются сами при старте:

```python
# src/procurement/apps.py
class ProcurementConfig(AppConfig):
    def ready(self) -> None:
        from src.core.identity.registry import register_party_profile
        from .models import VendorProfile
        register_party_profile(VendorProfile, title="Закупки")
```

`get_party_360(party_id)` обходит реестр и собирает все существующие профили.
Прямых импортов модулей в ядре нет — проверяется `lint-imports`.

### 4.3 Ленивое создание

```python
def get_or_create_profile(profile_model: type[M], entity_id: UUID) -> M
```

Профиль появляется в момент первой надобности. Контрагент, с которым работают
только закупки, имеет ровно один профиль.

## 5. Процессы

### 5.1 Создание контрагента

```
запрос на создание
   │
   ├─► find_party_duplicates(inn, kpp, short_name)
   │        │
   │        ├─ точное совпадение по ИНН+КПП ──► DuplicatesFound(score=1.0)
   │        └─ триграммное сходство по short_name > порога ──► DuplicatesFound
   │
   ├─ дубликатов нет ──────────────► создать, status=DRAFT
   └─ дубликаты есть, force=False ─► DuplicatesFound со списком кандидатов
      дубликаты есть, force=True ──► создать (решение принял человек, пишется в аудит)
```

**Инвариант И5:** `Party.objects.create()` в прикладном коде запрещён.
Единственная точка входа — `core.identity.services.create_party()`.

Сигнатуры:

```python
def create_party(data: PartyCreateDTO, *, force: bool = False,
                 actor_id: UUID) -> Party: ...
def update_party(party_id: UUID, data: PartyUpdateDTO, *, actor_id: UUID) -> Party: ...
def archive_party(party_id: UUID, *, actor_id: UUID, reason: str) -> None: ...
def merge_parties(primary_id: UUID, duplicate_id: UUID, *, actor_id: UUID) -> None: ...
```

**Актор передаётся как `UUID`, а не как объект `User`.** По слоевому контракту
`core.identity` лежит ниже `core.accounts`, поэтому ядро идентичности физически
не может импортировать `User`. То же правило действует для событий и аудита:
актор везде хранится идентификатором без внешнего ключа. Проверку прав выполняет
вызывающая сторона — API или админка, — а сервис только фиксирует, кто совершил
действие.

`merge_parties` архивирует дубликат и оставляет ссылку `merged_into`, чтобы старые
идентификаторы разрешались. Профили не сливаются автоматически — модули получают
событие и решают сами.

### 5.2 Дедупликация

```python
def find_party_duplicates(
    inn: str = "", kpp: str = "", name: str = "",
    threshold: float | None = None,   # по умолчанию из настроек, 0.4
) -> list[DuplicateMatch]
```

Порядок: точное по `(inn, kpp)` → триграммное по `short_name`, топ-10, исключая архивные.
`DuplicateMatch` содержит `party`, `score` (Decimal), `reason` («ИНН» или «название»).

**Нечёткое сравнение выполняется оператором `%`, а не функцией `similarity()`.**
GIN-индекс с `gin_trgm_ops` обслуживает только оператор; выражение
`similarity(a, b) > 0.4` индекс использовать не может и всегда даёт Seq Scan.
Порог задаётся через `pg_trgm.similarity_threshold`:

```python
from django.contrib.postgres.search import TrigramSimilarity  # только для score
from django.db import connection

with connection.cursor() as cur:                    # порог на транзакцию
    cur.execute("SELECT set_limit(%s)", [threshold])

qs = (Party.objects
      .exclude(status=PartyStatus.ARCHIVED)
      .filter(short_name__trigram_similar=name)     # оператор %, идёт в индекс
      .annotate(score=TrigramSimilarity("short_name", name))
      .order_by("-score")[:10])
```

`django.contrib.postgres` обязателен в `INSTALLED_APPS` — без него лукап
`__trigram_similar` не регистрируется.

Порог выносится в настройку `IDENTITY_DEDUP_THRESHOLD` — калибруется на реальных данных
после первой миграции из 1С.

### 5.3 Статусные переходы

```
DRAFT ──► ACTIVE ──► BLOCKED ──► ACTIVE
  │          │           │
  └──────────┴───────────┴──► ARCHIVED  (обратного пути нет)
```

`ARCHIVED` терминален. Удаления записей нет вообще.

### 5.4 Промоушен кандидата

Кандидаты живут в модулях (`procurement.VendorCandidate`, `crm.Lead`) без ИНН
и без валидации. В ядро поднимаются при первом реальном событии — заявке на закупку,
договоре, квалифицированной сделке.

```python
# вызывается модулем через фасад ядра
def promote_to_party(data: PartyCreateDTO, *, force: bool = False,
                     actor: User) -> Party
```

Модуль обязан сохранить `promoted_to` у кандидата и больше не создавать дублей.

| Событие | Когда | Полезная нагрузка |
|---|---|---|

Подписчиков в Фазе 0 нет — контракт заводится заранее.

## 7. Права доступа

| Операция | Кто |
|---|---|

## 10. Открытые вопросы

1. ~~Уникальность `Item.code`~~ — **закрыт.** Подтверждено: в 1С коды между типами
   номенклатуры не пересекаются. Уникальность глобальная, `unique=True` на поле.
2. **Статус `obsolete` («снято с производства») для номенклатуры** — нужен ли отдельно
   от `archived`? Зависит от того, как ведётся снятие с производства сейчас.
3. **Порог триграммного сходства** — 0.4 взят по умолчанию. Калибруется после первой
   выгрузки из 1С на реальных наименованиях.
4. **Слияние профилей при `merge_parties`** — сейчас модули решают сами по событию.
   Возможно, для части профилей нужна автоматика.
5. ~~Головные организации и филиалы~~ — **закрыт.** Замер по рабочей базе:
   3 обособленных подразделения и 3 филиала на 1904 контрагента (0,2%).
   Восьмое поле в `Party` не заводим — объём не оправдывает расширение ядра.
   Филиалы остаются отдельными `Party` со своими КПП; если связь с головной
   организацией когда-нибудь понадобится, её место в профиле модуля, которому
   она нужна, а не в ядре.
6. **Обогащение через ДаData** — на этапе создания синхронно или фоном? Влияет на UX
   мастера создания. Реализуется не в Фазе 0.
7. ~~Общий префикс в наименованиях гасит триграммный поиск~~ — **закрыт, ответ
   оказался противоположным ожидаемому.** Проверено на выгрузке `Catalog_Контрагенты`
   из рабочей базы, 1906 записей:

   | Где организационно-правовая форма | Записей |
   |---|---|
   | в конце наименования («Инвестехэнерго ООО») | 981 (51%) |
   | отсутствует вовсе («СИНТО», «Аэрофлот») | 911 (48%) |
   | в начале («ООО Ромашка») | 13 |

   Общего префикса нет, триграммный поиск деградировать не будет. Отдельное поле
   `search_name` **не требуется** — GIN-индекс на `short_name` работоспособен.

   Но нормализация при сравнении всё равно нужна, и снимать форму надо **с конца**,
   а не с начала. Дополнительно в данных: 841 запись (44%) целиком в верхнем регистре,
   102 с двойными пробелами внутри, 72 с кавычками. Нормализация перед сравнением:
   нижний регистр → снятие формы из хвоста → удаление кавычек и лишних пробелов.

   Реализуется функцией нормализации в `services/dedup.py`, применяемой к обеим
   сторонам сравнения. Хранимого поля не заводить.
