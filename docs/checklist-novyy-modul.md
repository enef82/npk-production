# Чек-лист: создание нового модуля

Пошаговый порядок сборки нового функционального модуля (`crm`, `contracts`, `hr`,
`finance`, `projects`, `production`, `intelligence`) по образцу `procurement`
(`docs/adr/0001-shablon-modulya.md`). Каждый шаг называет файл-образец в
`src/procurement/` — при сомнении, что и как писать, сначала открыть его.

Перед началом — прочитать спецификацию модуля в `docs/spec/` (если она ещё не
написана, писать не с нуля: спецификация закупок ИС (IS_ERP, 30-procurement) — образец формы спецификации
для среза). При расхождении спецификации с заданием спецификация главнее
(роадмап Фазы 0 ИС, «Правило приоритета»).

---

## 0. Скелет (генератор — минуты, не часы)

```bash
uv run python scripts/new_module.py <name> "<verbose_name>"
```

Создаёт файловую структуру раздела 4 CLAUDE.md с докстрингами-заглушками:
`apps.py`, `models/__init__.py`, `migrations/__init__.py`, `admin/__init__.py`,
`api/{__init__,routers,schemas,filters}.py`, `services/__init__.py`, `selectors.py`,
`facade.py`, `events.py`, `handlers.py`, `rules.py`, `tasks.py`,
`tests/{__init__,factories}.py`.

**Дальше — руками, генератор этого не делает** (риск повредить общий конфиг
автоматической правкой важнее сэкономленных двух минут):

1. Добавить `"src.<name>"` в `INSTALLED_APPS` (`config/settings/base.py`).
2. Добавить контракт `facade-<name>` в `.importlinter` (запрет импорта
   `src.<name>.{models,services,selectors}` из остальных функциональных модулей —
   скопировать существующий блок `facade-procurement` и переименовать).
3. `uv run python manage.py makemigrations` появится доступен только после первой
   модели — на этом шаге пропустить.

## 1. Модели

Образец: `src/procurement/models/{vendor_profile.py, purchase_category.py,
vendor_candidate.py, choices.py}`.

- Профиль поверх ядра — наследник `core.identity.profiles.PartyProfile`/`ItemProfile`,
  регистрируется в `apps.py::ready()` через `register_party_profile`/
  `register_item_profile` (см. `src/procurement/apps.py`).
- Статусы — только `TextChoices` в `models/choices.py`, никаких строковых литералов
  в коде.
- Конечный автомат — `django-fsm-2`: `FSMField(protected=True)` + голые
  `@transition`, без логики внутри (логика в `services/`). Образец:
  `models/vendor_profile.py`.
- Справочник со своим деревом — `parent` FK на себя, `PROTECT`, без treebeard.
  Образец: `models/purchase_category.py`.
- **Справочник заводится тогда и только тогда, когда по его значению считается отчёт
  или срабатывает правило** (CLAUDE.md §5). Иначе он даёт выпадающий список, в котором
  выбирают «прочее». Критерий один и тот же в обе стороны: типам вложений заявки
  справочник не нужен (§3.10), причинам проигрыша — необходим (§3.9).
- **Тот, кто выбирает значение из справочника, не расширяет справочник.** Роль,
  фиксирующая факт (менеджер выбирает причину проигрыша), не получает права заводить
  новые значения: в момент, когда подходящего нет, она заведёт своё вместо того, чтобы
  выбрать ближайшее или спросить, — и классификатор разъедется. Право на ведение
  справочника, влияющего на результат, — **собственное `can_*` (`has_perm`), выданное
  роли через `core.accounts.groups.SEED_GROUP_PERMISSIONS`**, а не переиспользование
  роли: когда справочник передадут другому человеку, меняется состав держателей права,
  а не код. Образец — `crm.rules.can_manage_loss_reasons`, `core_costing.manage_reference`.
- `@track()` на каждую модель, которой нужен аудит (обычно — все, кроме чисто
  технических).
- Первичный ключ — `UUIDPrimaryKeyModel`, кроме таблиц-расширений «один к одному»
  (сам `party`/`item` как PK, см. CLAUDE.md §5).
- FK на другой функциональный модуль — запрещены (И2). Только UUID-поле без FK.

`uv run python manage.py makemigrations <name>` → проверить сгенерированное имя
файла, переименовать в осмысленное (`0001_initial` подходит для первой миграции
модуля без изменений).

## 2. Роли и права

Образец: `src/procurement/rules.py`, `src/core/accounts/{groups.py, rules.py,
facade.py}`.

- Новая роль — константа в `core.accounts.groups.SEED_GROUP_NAMES` (роли — общий
  вокабуляр всей системы, живут в `core.accounts`, не в модуле).
- Предикат по роли — в `core.accounts.rules`, экспортируется через
  `core.accounts.facade` (общий предикат, как `is_administrator`).
- Предикат, специфичный модулю (например, переиспользующий чужое Django-право,
  как `is_data_administrator` в `procurement.rules`) — прямо в `<module>/rules.py`.
- Права работают одинаково в admin и API — один и тот же предикат в обоих
  местах, не два разных способа проверки.
- Если понадобится `@rules.predicate` — добавить mypy override в `pyproject.toml`
  (`disallow_untyped_decorators = false` для `src.<name>.rules`, скопировать
  существующую запись для `src.procurement.rules`).

## 3. Сервисы

Образец: `src/procurement/services/{vendor_profile.py, category.py, candidate.py}`.

- Функции, не классы (CLAUDE.md §5). `actor_id: UUID`, не `User` — если сложное
  разрешение прав не требует полного объекта пользователя внутри сервиса
  (сравнить `core.identity.services.party` vs. `core.approvals.services.approval`,
  где `by_user: User` нужен для делегирования).
- `transaction.atomic()` + `actor_context(actor_id, **extra)` — единственное место
  транзакций для моделей модуля (проверяется AST-тестом,
  `tests/test_invariant_transactions.py`).
- Права НЕ проверяются внутри сервиса (кроме случаев со сложным разрешением, как в
  `core.approvals`) — проверка в `api/routers.py`/`admin` перед вызовом.
- Событие публикуется `publish(...)` внутри той же транзакции, что меняет
  состояние (И4) — после, не до и не вне.
- Дубликаты/промоушен во внешние сущности ядра — через `core.identity.facade`
  (`create_party`/`create_item`, `force=False` по умолчанию,
  `DuplicatesFound` наружу). Образец: `services/candidate.py`.

## 4. Selectors и facade

Образец: `src/procurement/selectors.py`, `src/procurement/facade.py`.

- Список — без N+1: `select_related`/`prefetch_related` в базовом queryset
  селектора, фильтры накладываются поверх в `api/filters.py`.
- Дерево — рекурсивный CTE (`WITH RECURSIVE`), не treebeard. Образец:
  `list_category_and_descendant_ids`.
- `facade.py` — только то, что реально нужно другому модулю СЕЙЧАС, с докстрингом
  «кто первый потребитель». Ничего «на будущее».

## 5. События

Образец: `src/procurement/events.py`, `src/procurement/handlers.py`,
`docs/events.md`.

- `event_type` строго по формату `<модуль>.<сущность>_<действие_в_прошедшем>`
  (подчёркивание, не точка) — см. правило в `docs/events.md`.
- Каждое новое событие — запись в каталоге `docs/events.md` по шаблону файла,
  в том же PR, что его вводит.
- Подписка — `@subscribe("...")` в `handlers.py`, обработчик идемпотентен
  (проверяется тестом: повторная доставка не меняет состояние повторно).
- Обработчик не публикует событий сам, если это не самостоятельное пользовательское
  действие, а следствие чужого события — исходное событие уже отражено в каталоге,
  дублировать не нужно (см. `procurement.vendor_blocked` про `force_block`).
- **Публикацию нового события проверять напрямую** (`OutboxEvent.objects.get(event_type=...,
  aggregate_id=...)`), а не только косвенно через реакцию подписчика. Реальный
  прецедент: `identity.party_archived` до шага 11 существовал в спеке, но не
  публиковался кодом (`archive_party()` не звал `publish()`) — задание на шаг 3
  событие прямо исключало. Тест на стороне подписчика (`procurement`), не
  проверяющий сам факт публикации, прошёл бы одинаково — как при работающей
  публикации, так и без неё, если бы что-то другое случайно приводило профиль в
  `BLOCKED`. Прямая проверка (`src/core/identity/tests/test_party_service.py`)
  на это не полагается.
- **Если тестовая фикстура трогает глобальный реестр (обработчики событий,
  `core.identity.registry._party_profiles`/`_item_profiles`, что угодно
  накопительное на уровне модуля/процесса) — она обязана восстанавливать
  состояние, а не только очищать его.** Реальный прецедент: `_clean_registry`
  (`src/core/events/tests/conftest.py`, autouse) до шага 11 просто вызывал
  `registry.clear()` до и после каждого теста — стирая не только тестовые
  подписки, но и обработчики, зарегистрированные один раз при старте приложения
  (`autodiscover_modules("handlers")`). Пока в системе не было ни одного
  постоянного обработчика, дефект был невидим; `procurement.handlers` стал первым
  и тут же проявил его — любой тест из `core.events.tests`, выполнившийся раньше
  в той же сессии `pytest`, «выключал» чужой обработчик до конца сессии. Снимок +
  восстановление вместо голого `clear()`, и тест на саму фикстуру (не на
  спонтанную удачу, что баг снова будет замечен): `src/core/events/tests/
  test_conftest.py` — зарегистрировать «постоянный» обработчик, прогнать
  снимок/очистку/восстановление, убедиться, что он на месте, а всё, что
  подписалось после снимка, — нет.

## 6. Admin

Образец: `src/procurement/admin/__init__.py`.

- Модель с сервисом, владеющим переходом/побочным эффектом → поля, которыми
  владеет сервис, `readonly_fields`; изменение — действием или `save_model`,
  роутящим в сервис (не `obj.save()` напрямую).
- M2M-поле, которым владеет сервис, — отдельное поле формы (не через
  `Meta.fields`), иначе `ModelForm.save_m2m()` запишет его в обход сервиса сразу
  после `save_model`. Образец: `VendorProfileAdminForm`.
- Действие, которому нужна форма (не просто bulk-операция без параметров) —
  custom view через `get_urls()` + `admin_site.admin_view(...)`, редирект на
  changelist по завершении. Образец: `VendorCandidateAdmin.promote_view`.
- `has_add_permission`/`has_change_permission` — через предикат из `rules.py`
  (не голый Django `has_perm`, если модуль ввёл собственные роли).
- `register_history(...)` для каждой `@track()`-модели в конце файла.

## 7. API

Образец: `src/procurement/api/{routers.py, schemas.py, filters.py}`.

- Курсорная пагинация — `core.common.pagination.paginate_cursor`/`CursorPage`,
  не декоратор `@paginate` (сортировка задаётся запросом, не фиксируется на этапе
  декоратора).
- `FilterSchema` в `filters.py`, `Query(...)` в сигнатуре роутера.
- Права — `if not predicate(request.auth): raise PermissionDenied(...)` до вызова
  сервиса.
- Роутер подхватывается автомонтированием `config/api.py` — ничего вручную
  регистрировать не нужно, эндпоинты `/api/v1/<label>/...`.
- Не каждое действие обязано быть в API — сверить со спецификацией модуля, что
  именно нужно фронтенду, а не переносить туда всё из admin автоматически
  (пример — продвижение кандидата в `procurement`, только admin).

## 8. Фронтенд

Образец: `frontend/app/(protected)/vendors/`, компоненты
`frontend/components/{data-table,entity-card,entity-form}/`.

1. `make api` (или вручную: `python manage.py export_openapi_schema --api
   config.api.api --output openapi.json --indent 2`, затем `cd frontend && npx
   orval --config orval.config.ts`) — без этого новые эндпоинты не видны
   типобезопасно.
2. Список — `page.tsx` + `<name>-view.tsx` + `columns.tsx` + `<name>-toolbar.tsx`,
   `DataTable` + `useTableUrlState` + `useKnownTotal`.
3. Карточка — `[id]/page.tsx` + `<name>-card-view.tsx`, `EntityCard` с вкладками.
4. Экраны собираются **без правок** в `components/data-table/*`,
   `components/entity-card/*`, `components/entity-form/*`. Если правки
   понадобились — интерфейс компонента недоделан, чинить компонент, не обходить
   в модуле.
5. Пункт в `frontend/components/layout/nav-items.ts` (снять `disabled: true`,
   поправить `href` на реальный маршрут).
6. `npx tsc --noEmit` и `npx eslint <изменённые файлы>` — оба чистые до коммита.
7. **`queryClient.invalidateQueries` — ключом из сгенерированного `getGet<Entity>
   QueryKey(id)`/`getList<Entities>QueryKey(params)`, никогда не «руками» по
   образцу с чужого экрана.** Реальный дефект, найденный на этом шаге при первом
   запуске в браузере (не отловлен ни `tsc`, ни `eslint`, ни pytest): написанный по
   аналогии с `parties-view.tsx` ключ `["/api/v1/procurement/vendors", { partyId }]`
   не совпадал с настоящим `[`/api/v1/procurement/vendors/${partyId}`]`, который
   кладёт `useGetVendor` — `invalidateQueries` тихо не находил запись в кеше.
   Мутация на сервере проходила корректно, тост показывался, а карточка молча
   продолжала показывать состояние до мутации до ручного обновления страницы.
   Тип-система здесь бессильна: обе строки — валидные `string[]`, несовпадение
   чисто по значению. **Обязательно открыть экран в браузере и проверить, что
   статус/данные обновляются без ручного `F5` после каждого мутирующего действия**
   (CLAUDE.md: «для UI-изменений — запустить dev-сервер и опробовать в браузере»,
   не полагаться только на `tsc`/`eslint`/юнит-тесты).

## 9. Тесты

Раздел 8 CLAUDE.md, образец — `src/procurement/tests/`.

| Файл | Что покрывает |
|---|---|
| `test_<model>.py` | статусные переходы (разрешённые и запрещённые —
  `django_fsm.TransitionNotAllowed`), N+1 на списках (`assertNumQueries`/`CaptureQueriesContext`) |
| `test_purchase_category.py` (по аналогии) | `IntegrityError`/`ProtectedError` на ограничениях БД |
| `test_rules.py` | предикаты напрямую + 403/200 сквозь API |
| `test_events.py` | публикация в транзакции, откат не оставляет `OutboxEvent` |
| `test_handlers.py` | идемпотентность обработчика при повторной доставке |
| `test_admin.py` | admin идёт через сервис — наблюдаемый результат (не мок вызова) |

Если инвариант завязан на несколько модулей сразу (как независимость профилей
`core.identity`) — тест живёт в корневом `tests/`, а не в `src/<module>/tests/`
или `src/core/.../tests/`, если это нарушило бы `.importlinter`
(`core-independence`/`core-layers`). Проверить `uv run lint-imports` до, а не
после того, как тест написан.

**Любое состояние, живущее дольше одного теста — не только в БД, но и вне БД,
включая файловое хранилище, — обязано либо восстанавливаться/очищаться фикстурой, либо
быть явно принятым и задокументированным как известный компромисс.** Такое
восстановление обязано быть проверено собственным тестом, а не оставлено на
внимательность при код-ревью. Три подтверждённых случая одного класса дефекта:

1. `_clean_registry` до шага 11 (`src/core/events/tests/conftest.py`) стирал не
   только тестовые подписки на события, но и постоянные обработчики, зарегистрированные
   при старте приложения — обнаружилось только когда появился первый постоянный
   обработчик.
2. `--reuse-db` (`pyproject.toml`) до шага 1 Фазы 1 не восстанавливал данные, посеянные
   `RunPython`-миграциями, после `flush()` любого `django_db(transaction=True)`-теста —
   обнаружилось только когда появился первый тест, проверяющий состав данных такой
   миграции (`conftest.py` в корне репозитория, `ensure_core_reference_data`).
3. `DocumentFactory()`/S3-хранилище (`src/core/documents/tests/factories.py`,
   `test_access.py`) реально загружает файл в MinIO при каждом вызове — это происходит
   вне транзакции Django-теста и потому не откатывается вместе со строкой `Document`.
   На момент обнаружения (шаг 2 `crm`, при разборе не связанного с этим флейка) в
   локальном бакете накопилось 2310 никогда не удалявшихся объектов, по 19 новых за
   один прогон `src/core/documents` (22 теста). Дефект отличается от первых двух тем,
   что признан, но **не устранён в этом шаге** — исправление требует решения о
   механизме очистки (autouse-фикстура, отдельный тестовый бакет с TTL-политикой и т.п.),
   которое здесь не принималось; заводите ADR или отдельную задачу, а не тихую правку
   заодно с несвязанным шагом.

Во всех трёх случаях дефект был невидим ровно до первого теста, которому реально
понадобилось восстановленное состояние, или до первого прямого замера — не
полагайтесь, что для нового модуля такого теста/замера не найдётся. Закладывайте
восстановление сразу, если модуль вводит новую разновидность общего состояния (реестр,
посеянные миграцией справочные данные, файлы во внешнем хранилище и т.п.), и покрывайте
само восстановление тестом по образцу `src/core/events/tests/test_conftest.py` /
`tests/test_conftest.py`. Если восстановление в моменте не по силам (как со случаем 3)
— фиксируйте это письменно здесь же или в ADR, а не молчанием.

Две смежные ловушки на том же шаге, стоит знать заранее:

- **Корневой `conftest.py` — только в корне репозитория, не в `tests/`.**
  `testpaths = ["tests", "src"]` (`pyproject.toml`) — сиблинги, не вложены друг в
  друга; `conftest.py` внутри `tests/` не действует на тесты под `src/*/tests/`.
  Фикстура, которая должна работать для всего проекта, но лежит в `tests/conftest.py`,
  молча не сработает ни на одном тесте вне `tests/` — именно так и было обнаружено:
  тест был зелёным на `--create-db` не из-за фикстуры, а из-за того, что миграция
  только что отработала сама.
- **Список контрольных данных для восстанавливающей фикстуры и список для теста,
  проверяющего состав миграции — общий модуль, не две отдельные копии.** Если у
  фикстуры и у теста разные копии одного и того же списка, тест на переиспользуемой
  БД (`--reuse-db`) подтверждает только то, что фикстура согласна сама с собой, а не
  то, что миграция действительно сеет ожидаемый состав — расхождение миграции со
  спецификацией тогда не поймает никто. Держите ровно два независимых списка (миграция
  как продакшен, общий тестовый модуль как спецификация), а не три — образец:
  `tests/reference_data.py`, `conftest.py::ensure_core_reference_data`,
  `src/core/costing/tests/test_cost_article.py`. Такой тест доказателен только при
  `pytest --create-db` — зафиксируйте это прямо в его докстринге, не полагайтесь, что
  читатель сам выведет это из механики фикстуры.

## 10. Playwright (если есть фронтенд-экран)

Образец: `frontend/tests/e2e/vendors.spec.ts`, хелпер `frontend/tests/e2e/helpers.ts`.

- Логин через `login(page)` из `helpers.ts` (учётка суперпользователя из `make seed`).
- Фильтр меняет URL, состояние переживает `page.reload()`.
- Действие, меняющее состояние сущности (переход статуса и т.п.), отражается
  и в карточке, и в списке.

## 11. Проверка перед сдачей

```bash
make lint   # ruff check/format, mypy config src, lint-imports
make test   # pytest — включая новые тесты модуля
make mm     # миграции не разошлись с моделями
```

Все три — зелёные. Красный `make lint`/`make test` = задача не выполнена
(CLAUDE.md §9).
