# CLAUDE.md — конституция проекта

Этот файл читается в начале каждой сессии. Правила здесь имеют приоритет над любыми
общими привычками и «best practices». Если задание противоречит этому файлу — остановись
и спроси, а не выбирай самостоятельно.

## 1. Что за проект

Приложение «НПК Производство» — автономное веб-приложение управления производством
инжиниринговой компании: заявки и калькуляция, производственные заказы и план-график,
ОТК, снабжение, табель, оборудование и ТО, энергоучёт, аналитика. Построено по прототипу
«Производство» и по правилам корпоративной ИС (репозиторий `enef82/IS_ERP`): тот же стек,
те же инварианты, то же ядро (`src/core` скопировано из ИС). Модули устроены так, чтобы
позже переехать в ИС модулями. **Модульный монолит на Django** с событийной связью модулей.

Восемь функциональных блоков: `sales`, `production`, `quality`, `supply`, `timesheet`,
`equipment`, `energy`, `analytics` и платформенное ядро `core`. Функциональная
спецификация — `docs/spec/00-prilozhenie-proizvodstvo.md`.

Команда — 1–2 разработчика. Из этого следует главное требование к коду: **он должен быть
скучным, предсказуемым и одинаковым во всех модулях**. Любая «умная» конструкция, которую
через год не поймёт второй человек, — это дефект, а не достижение.

### Границы системы

Система — надстройка над 1С, а не замена ей. **Никогда не реализуй в этом проекте:**
бухгалтерский и налоговый учёт, расчёт заработной платы, НДФЛ и взносов, отчётность
в СФР и ФНС, ЭДО, кадровый ЭДО, электронную подпись. Это остаётся в 1С и внешних сервисах.
Если задача выглядит так, будто требует что-то из этого списка, — остановись и спроси.

## 3. Нерушимые архитектурные инварианты

Нарушение любого из них — блокирующий дефект.

### И1. Модули общаются только через фасады

Модуль импортирует из соседнего модуля **исключительно** `facade.py`.
Импорт чужих `models`, `services`, `selectors` запрещён и проверяется `import-linter` в CI.

```python
# ЗАПРЕЩЕНО
from src.procurement.models import VendorProfile

# ПРАВИЛЬНО
from src.procurement import facade as procurement
summary = procurement.get_vendor_summary(party_id)
```

Ядро `core` доступно всем. `core` не знает ни об одном функциональном модуле.

**Узкое исключение: `get_user_model()` в модулях ниже `core.accounts` по слоевому
контракту.** `import-linter` проверяет только явные `import`-операторы — `AUTH_USER_MODEL`
и `django.contrib.auth.get_user_model()` дают доступ к модели пользователя в обход этой
проверки, и связность от этого никуда не девается, просто перестаёт быть видна линтеру.
Разрешено это только там, где изменение учётной записи обязано быть атомарным с изменением
состояния в той же транзакции (пример — отзыв доступа при увольнении сотрудника:
`core.org.services.employee.terminate_employee`). Доменное событие здесь не годится:
диспетчер `core.events` асинхронный (обработка — до `EVENTS_DISPATCH_INTERVAL_SECONDS`
секунд), а для отзыва доступа окно, в котором уволенный ещё может войти, недопустимо;
событие также не гарантирует обработку (упавший обработчик = доступ не отозван).
Во всех остальных случаях связь между модулями ядра идёт через доменное событие или facade,
а не через `get_user_model()`. Это осознанное исключение, а не прецедент для повторного
использования без такого же обоснования — на каждом месте использования обязателен
комментарий, объясняющий, почему здесь нужна атомарность, а не событие.

### И2. Внешние ключи между модулями запрещены

Разрешены только FK на `core`. Связь с сущностью другого модуля — через UUID-поле
без `ForeignKey` плюс обращение к фасаду.
Единственное задокументированное исключение — `hr.CostObject` (см. спецификацию кадров).

### И3. Транзакции открываются только в `services/`

Ни в `api/`, ни в `admin/`, ни в моделях, ни в `tasks.py`. Сервис — единственное место,
где меняется состояние. API и админка вызывают сервис.

### И4. События пишутся в той же транзакции, что и изменение состояния

```python
with transaction.atomic():
    contract.status = ContractStatus.SIGNED
    contract.save(update_fields=["status"])
    publish(ContractSigned(contract_id=contract.id, party_id=contract.party_id))
```

Никаких публикаций после `commit`, никаких прямых вызовов чужих обработчиков.

### И5. Записи в ядро идентичности создаются только через сервис

`Party.objects.create()` и `Item.objects.create()` в прикладном коде запрещены.
Только `core.identity.services.create_party()` / `create_item()` — они обязаны выполнить
проверку на дубликаты.

### И6. Деньги — только `Decimal`

`MoneyField` (DecimalField с `max_digits=18, decimal_places=4`). `float` для денег и
количеств запрещён абсолютно, включая промежуточные вычисления и тесты.

### И7. Первичен ввод разноски, свод — производная

В подсистеме табеля `TimesheetEntry` никогда не создаётся и не правится напрямую,
только пересчитывается из `WorkAllocation`.

## 4. Структура модуля

Все модули устроены одинаково. Отклонения не допускаются.

```
src/<module>/
├── apps.py
├── models/           # только определение данных; логики нет
├── migrations/
├── admin/            # справочники, настройки, backoffice
├── api/
│   ├── routers.py    # эндпоинты django-ninja
│   ├── schemas.py    # Pydantic in/out
│   └── filters.py
├── services/         # бизнес-логика; ЕДИНСТВЕННОЕ место транзакций
├── selectors.py      # запросы на чтение, агрегаты, отчёты
├── facade.py         # публичный интерфейс модуля для других модулей
├── events.py         # события, которые модуль публикует (dataclass)
├── handlers.py       # обработчики чужих событий
├── tasks.py          # Celery — только оркестрация, логика в services
├── rules.py          # предикаты прав доступа
└── tests/
```

## 5. Конвенции кода

- **Сервисы — функции, а не классы.** `def approve_requisition(requisition_id: UUID, user: User) -> None`.
  Классы-сервисы заводить только при реальном состоянии, чего почти не бывает.
- в `services/` живёт логика, меняющая состояние; чистые функции — валидаторы, форматтеры, расчёты без БД — лежат отдельными модулями. Это и цикл снимает, и делает сервисный слой честным.
- Если у модели есть сервис, владеющий переходом или побочными эффектами, поля, которыми он управляет, в админке доступны только для чтения, а изменение выполняется действием, вызывающим сервис. Либо `save_model` маршрутизируется в сервис.
- **Модели тонкие.** В модели допустимы: поля, `Meta`, `__str__`, простые `@property`
  без обращений к БД. Всё остальное — в сервис или селектор.
- **Никаких сигналов Django для бизнес-логики.** Сигналы допустимы только для технических
  задач (инвалидация кэша). Реакция на изменение состояния — через события из `core.events`.
- **Статусы — только `TextChoices`.** Строковых литералов статусов в коде быть не должно.
- **Типизация обязательна** в `services/`, `selectors.py`, `facade.py`. `mypy` без ошибок.
- **`verbose_name` на русском** у каждого поля и модели. Интерфейс полностью русский,
  включая админку и сообщения об ошибках. Имена в коде — английские.
- **`null=True` на строковых полях запрещён**, используй `blank=True` и пустую строку.
- **Первичные ключи — UUIDv7 (`UUIDPrimaryKeyModel`) у всех сущностей**, кроме таблиц-
  расширений «один к одному» (профили поверх `Party`/`Item` и им подобные): там первичным
  ключом должен быть сам внешний ключ на расширяемую сущность
  (`OneToOneField(..., primary_key=True)`), а не отдельный суррогатный `id`. Отдельный `id`
  у такой таблицы избыточен и создаёт непредсказуемость: одни сущности с UUID, другие
  с целыми — и каждый разработчик обязан помнить, где какой. Естественный ключ профиля —
  это ключ его `Party`/`Item`.
- **Ограничения — в БД.** Уникальность, диапазоны, взаимоисключающие поля выражай через
  `UniqueConstraint`, `CheckConstraint`, `ExclusionConstraint`, а не только валидацией в Python.
- **N+1 недопустим.** В любом списочном запросе — `select_related` / `prefetch_related`.
  В тестах списков используй `assertNumQueries`.
- **Миграции** — по одной на логическое изменение, с осмысленным именем
  (`0007_add_vendor_rating`, не `0007_auto_20260819`).
- **Комментарии объясняют «почему», а не «что».** Код объясняет «что» сам.
- **Свободный текст или сущность — решается до накопления данных.** Текстовое поле
  допустимо, пока значение читает только человек и только там, где он уже находится.
  Как только по значению нужно **искать, фильтровать, считать отчёт, перейти к другому
  объекту или проверить правило** — это перестаёт быть текстом и становится полем,
  справочником или самостоятельной сущностью.

  Правило работает в обе стороны. Справочник, по значению которого ничего не происходит, —
  вред: он даёт выпадающий список, в котором семь раз из десяти выбирают «прочее».
  Свободная строка, по которой строится отчёт, — тоже вред: «дорого», «цена»
  и «не прошли по цене» станут тремя разными причинами.

  Решение принимается **до того, как записи накопились**: превратить свободный текст
  в структуру задним числом — ручная работа по каждой записи, а не миграция. При сомнении
  вопрос задаётся сразу, а не откладывается до отчёта.

  **Если известно, что значение станет сущностью в следующей фазе, оно заводится
  сущностью сразу.** «Пока хватит текста, потом структурируем» — не компромисс,
  а перенос ручной работы на себя будущего: разобрать накопленные строки задним числом
  придётся по одной. Разное устройство одного и того же понятия в разных модулях
  нарушает главное требование §1 — одинаковость.

  Официальное письмо — всегда запись журнала переписки с номером, датой, направлением
  и корреспондентом: и в заявке, и в договоре, и в проекте. Ссылка на письмо — ссылка
  на запись, а не строка «по письму № 123 от 12.08» внутри комментария.
- **Версии зависимостей проверяются в реестре пакетов на момент задачи, а не по памяти.**
  Прежде чем зафиксировать или обновить версию в `pyproject.toml`, смотри актуальный
  релиз на PyPI — обучающие данные модели устаревают, а зафиксированная версия может
  быть уже небезопасной или недоступной. Это не гипотетический риск: Django 5.2.5 —
  подтверждённый случай, версия, правдоподобная как выбор «по памяти», уже требовала
  замены на security-релиз (5.2.6) к моменту публикации. Проверяй не только номер
  последней версии, но и архив security-issues пакета
  (`https://docs.djangoproject.com/en/stable/releases/security/` для Django и
  соответствующие security-advisories для остальных зависимостей).
- **Апгрейд рантайма или замена библиотеки проверяется по всем уже зафиксированным пинам,
  а не только по пакету, который стал поводом апгрейда.** Совместимость одного пакета с целевой версией
  ничего не говорит об остальных. Прецедент: апгрейд на Python 3.14 ради `uuid.uuid7()`
  из stdlib был отклонён, потому что `celery==5.6.3` в classifiers на PyPI заявляет
  поддержку только до 3.13 — при том что Django, psycopg и django-ninja уже совместимы
  (см. `docs/adr/0004-uuidv7-cherez-biblioteku.md`). Проверяй PyPI classifiers/requires-python
  каждого пина из `pyproject.toml`, а не только нового или обновляемого пакета.

## 6. Чего не делать

Список составлен по типовым ошибкам, которые модель совершает по умолчанию.

- ❌ Не придумывай поля, модели и сущности, которых нет в задании. Если чего-то не хватает —
  спроси. Лишнее поле в ядре стоит дороже, чем вопрос.
- ❌ Не добавляй «на будущее» абстракции, фабрики, интерфейсы и слои. Только то, что нужно сейчас.
- ❌ Не пиши бизнес-логику в `admin.py`, `api/`, моделях, сериализаторах, шаблонах.
- ❌ Не расширяй ядро идентичности. `Party` — 7 полей, `Item` — 6 полей. Всё остальное
  идёт в профиль модуля.
- ❌ Не создавай отдельные справочники контрагентов или номенклатуры внутри модуля —
  только профили поверх ядра.
- ❌ Не используй `GenericForeignKey` без явного разрешения — он ломает производительность
  отчётов и типизацию.
- ❌ Не мокай базу в тестах. Используй реальную PostgreSQL и `factory-boy`.
  Мокать можно только внешние HTTP-вызовы (1С, ДаData, LLM).
- ❌ Не пиши тесты, которые проверяют вызов метода. Тестируй наблюдаемый результат:
  состояние в БД, возвращённое значение, опубликованное событие.
- ❌ Не оставляй `TODO` без задачи. Либо делай, либо явно фиксируй в отчёте как нерешённое.
- ❌ Не форматируй и не рефактори файлы, не относящиеся к задаче.
- ❌ Не коммить `.env`, секреты, дампы данных.

## 7. Как работать над задачей

1. **Прочитай задание целиком.** Найди противоречия с этим файлом и со спецификациями
   в `docs/`. Если они есть — спроси до начала работы.
2. **Составь план** из шагов и покажи его. Не начинай писать код, пока план не подтверждён,
   если задача больше одного файла.
3. **Пиши код.** Сначала модели и миграции, затем сервисы, затем API и админка, затем тесты.
4. **Напиши тесты**, перечисленные в задании, плюс те, что считаешь нужными.
5. **Прогони проверки:** `make lint && make test`. Не считай задачу выполненной при красном CI.
6. **Отчитайся:** что сделано, какие решения приняты и почему, что осталось нерешённым,
   какие вопросы возникли.
7. **Отдельным разделом отчёта — правки в документации:** путь каждого файла и что
   именно в нём изменено. Правка документа, о которой не сказано, теряется: параллельно
   этот же файл правит человек, и одна из версий молча затирает другую. Это уже
   происходило.

**Спецификации (`docs/spec/`), роадмапы фаз и файлы заданий правит только заказчик
задачи.** Агент их читает, при расхождении с заданием останавливается и спрашивает,
но не редактирует — включая отметки о статусе шагов. Всё остальное в `docs/` (ADR,
`events.md`, чек-листы) агент правит сам и перечисляет в отчёте по пункту 7.

**Перед записью в существующий документ он читается целиком.** Замена файла своей
версией без чтения текущей — способ потерять чужие правки, а не способ сэкономить.

Если по ходу выясняется, что задание невыполнимо в заявленном виде, — остановись и объясни.
Не подгоняй решение и не упрощай задачу молча.

## 8. Тестирование

Обязательное покрытие для любого модуля:

| Что                                                                                            | Почему                                                                  |
| ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Денежные и количественные расчёты                                   | здесь генерация кода ошибается чаще всего |
| Статусные переходы, включая запрещённые                        | ядро бизнес-правил                                            |
| Права доступа: и разрешение, и запрет                               | запрет тестируют реже, ломается чаще           |
| Ограничения БД: попытка нарушить →`IntegrityError`                 | иначе constraint существует только на бумаге     |
| Публикация событий и атомарность (rollback → события нет) | основа связности модулей                                |
| Идемпотентность обработчиков событий                            | повторная доставка неизбежна                        |

Тест именуется предложением: `test_нельзя_создать_контрагента_с_дублирующимся_инн`.
Русские имена тестов допустимы и приветствуются — они читаются как спецификация.

CI прогоняет `make lint && make test`. Красный CI = задача не выполнена.

## 10. Документация проекта

### Раскладка и имена

Три места, и только три:

- `docs/spec/` — **функциональные спецификации модулей и глоссарий, больше ничего.**
  Имя — номер блока и смысловой хвост через дефис: `docs/spec/00-prilozhenie-proizvodstvo.md`,
  `docs/spec/02-yadro-identichnosti.md`, `docs/spec/03-platforma.md`.
- `docs/adr/` — архитектурные решения. Имя — **четырёхзначный номер и смысловой хвост**:
  `docs/adr/0001-shablon-modulya.md`, `docs/adr/0004-uuidv7-cherez-biblioteku.md`.
  Префикса «adr» в имени нет — папка и так называется `adr`.
- `docs/` (корень) — всё остальное, **без номера**: `docs/events.md`,
  `docs/checklist-novyy-modul.md`, роадмапы и задания для сессий. Слова в имени
  через дефис.

Переезд или переименование документа — это правка **каждой** ссылки на него в коде
и других документах. `tests/test_doc_references.py` обходит `docs/**/*.md` и
`src|config/**/*.py` и проверяет, что каждое упоминание `*.md` указывает на существующий
файл; красный тест = ссылка осиротела. Не заводи второй файл под тем же смыслом с чуть
другим именем — удали старый.

### Содержание

- **ADR** — 2–3 абзаца: контекст, выбор, отвергнутые альтернативы. Заводи при каждом
  нетривиальном решении.
- **ADR обязателен при отказе от рекомендации** — своей, чужой, из best practices или прямо
  предложенной в задаче (апгрейд версии, библиотека, паттерн). Отказ без записанного ADR —
  недокументированное решение, которое через полгода выглядит как забытая задача, а не как
  сознательный выбор. Фиксируй: что рекомендовалось, почему отклонено, и если отказ временный —
  условие пересмотра (конкретный, проверяемый триггер, не «когда-нибудь»). Образец —
  `docs/adr/0004-uuidv7-cherez-biblioteku.md`.
- `docs/events.md` — каталог доменных событий с версиями. Это публичный контракт,
  меняется только с версионированием.

При изменении архитектуры сначала обновляется документ, затем код.
